# 平台修改建议 · 建模表单（业务主键提示 + 属性排序）

> 提出背景：服务产品成本本体录入时，业务主键（stable_key）的选取规则对使用者不可见，且属性顺序一旦排错无法通过界面调整，只能删除重建。
> 日期：2026-10-27 ｜ 状态：P1/P2/二/2.4 已实现（2026-10-27，E2E 全绿）；P3 显式指定主键仍为可选未做

---

## 一、业务主键（stable_key）

### 1.1 现状事实

| 项 | 事实 |
|---|---|
| 建模表单 | 对象卡片只有「对象 ID / 对象名称 / 上级对象（父类）/ 描述 / 属性 / 关系」六块，**没有 stable_key 输入框** |
| 提交内容 | `collectFormOntology()` 只提交 `id / name / description / parent / attributes / relations / constraints`，**不含 stable_key** |
| 后端行为 | `_backfill_object_fields()`（`backend/api/router_ontologies.py:75-97`）自动补齐，三级回退：**第一个「必填 + string」属性 → 第一个 string 属性 → 第一个属性** |
| 对象 PATCH | `OntologyObjectPatch` 不含 stable_key，只做保留，改不了 |
| 界面提示 | **完全没有**——使用者不知道有这条规则，也不知道自己当前的主键会落到哪个属性上 |

### 1.2 建议（按优先级）

**P1 · 属性区增加规则说明文案**

在对象卡片的「属性」区块标题（或小标题）后面，增加一行说明文字：

> 第一个「必填 + 字符串」属性将被自动设为业务主键（stable_key）

- 位置：`renderObjectForms()` 中 `.form-section-title` 的「属性」标题旁，用现有的 `text-[10px] text-slate-500` 小字样式（与属性约束区说明文案同一视觉层级）。
- 措辞要点：说清"自动""第一个""必填+字符串"三个条件，让使用者知道顺序有意义。

**P1 · 实时标出当前会被选为主键的属性**

在属性行上给"命中主键规则"的那一行加一个可见标记（如 `🔑 主键` 徽标或小字提示），并随以下操作实时更新：勾选/取消必填、切换数据类型、上移/下移、新增/删除属性。

- 判定逻辑与后端一致，前端可复用同一套三级回退规则本地计算。
- 好处：使用者不用猜，改一行就能立刻看到主键是否漂移。
- 边界情况要一并覆盖：
  - 对象没有任何 string 属性 → 提示"将退化为第一个属性（非字符串），建议补一个字符串主键属性"；
  - 对象没有任何属性 → 提示"缺少属性，无法生成业务主键"。

**P2 · 对象卡片增加只读的「业务主键」回显位**

在对象卡片「描述」下方（或在保存后的本体详情页对象列表中）显示一行只读信息：`业务主键：attr_xxx`。不需要输入框，只做核对用途，避免"以为设了其实没设"。

**P3 · （可选）支持显式指定主键**

若业务上确实需要人工指定，则需后端配合：
- `OntologyObjectPatch` 增加 `stable_key` 字段，允许 PATCH 修改；
- 前端对象卡片增加「业务主键」下拉（选项 = 本对象的 string 属性列表），并在下拉旁保留自动规则说明；
- 后端校验：显式值必须是本对象存在的属性 id，否则 422。

## 二、属性上移 / 下移按钮

### 2.1 现状事实

属性行的操作区目前**只有「删除」**（`app.js:901`），没有任何排序控件。属性顺序由"添加顺序"决定，一旦顺序不对（例如想让 `attr_product_code` 排到第一位），只能把所有后续属性删除重建——**已填的 ID、名称、约束全部丢失**。这在本次 17 个对象、每对象 5~17 个属性的录入量下代价很高。

属性行当前布局（12 列网格，`app.js:896-901`）：

```
3列 属性ID | 3列 名称 | 2列 类型 | 2列 必填 | 1列 约束 | 1列 删除
```

### 2.2 建议

**在每个属性行的操作区增加「↑ 上移 / ↓ 下移」两个按钮**，与「删除」并列。

行为要求：
1. 点击 ↑ / ↓ 交换该属性与相邻属性在 `state.formObjects[idx].attributes` 中的位置，并立即重渲染属性区。
2. **首行的 ↑ 与末行的 ↓ 置灰不可点**（避免无意义点击）。
3. 移动后必须保留该行已填写的全部内容：属性 ID、名称、类型、必填状态、**折叠区里的约束值**（尤其枚举值较长，重填成本最高）。
4. 若移动导致主键命中行变化，同步刷新第一部分的「🔑 主键」标记。

### 2.3 实现锚点（供开发参考）

- 渲染位置：`renderObjectForms()`（`app.js:888-930`），属性行 HTML 在 `896-901`。建议把「删除」列从 `col-span-1` 调整为操作按钮组（↑ ↓ 删除），或把各输入列各收窄 1 列腾出空间。
- 新增函数 `moveAttr(idx, aidx, dir)`，与现有 `removeAttr`（`app.js:1078-1082`）同构：

```
function moveAttr(idx, aidx, dir) {
  syncFormObjectsFromDOM();        // 先把 DOM 上未同步的输入写回 state
  const list = state.formObjects[idx].attributes;
  const to = aidx + dir;
  if (to < 0 || to >= list.length) return;   // 边界直接忽略
  [list[aidx], list[to]] = [list[to], list[aidx]];
  renderObjectForms();
}
```

- 注意点：`syncFormObjectsFromDOM()` 必须在交换**之前**调用，否则约束折叠区里未触发 blur 的输入会丢。约束区 `attrConstraintRowHtml` 的输入始终存在于 DOM，因此"sync → 改 state → 重渲染"这条链路能保住已填值，与 `removeAttr` / `addAttr` 保持一致即可。

### 2.4 顺带建议（同一交互模式，可一并做）

- **关系行**同样只有「删除」（`app.js:912`），建议照搬 ↑ / ↓。
- **对象卡片之间**也没有排序控件（`app.js:916` 只有「+ 子对象 / 删除对象」），当对象数较多时（本项目 17 个）同样需要上下移动，建议一并支持。

## 三、收益小结

| 建议 | 解决的问题 |
|---|---|
| 属性区规则说明 | 主键规则黑箱，使用者不知道"顺序"和"必填+字符串"决定主键 |
| 主键命中实时标记 | 改一个属性就可能导致主键漂移，事后才发现成本高 |
| 属性 ↑ / ↓ 按钮 | 顺序错了只能删除重建，丢失已填的 ID/名称/约束（尤其中文枚举值很长） |
| 主键只读回显 | 保存后无法核对实际生效的主键 |

- `frontend/app.js`：

  - 新增 `pkHitIndex / pkAttrsFromDom / updatePkBadges / updatePkBadgesAll / bindPkBadgeEvents`：徽标/提示/回显按 DOM 实时值增量更新（不整卡重渲染，避免输入焦点丢失）；规则与后端三级回退一致

- `frontend/index.html`：编辑器头部（标题+保存/取消）`sticky top-0`（`main` 滚动容器内，长表单滚动时保存按钮始终可见）；表单底部按钮行改为「+ 添加对象 / 保存本体」双按钮
