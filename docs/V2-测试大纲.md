# 企业业务本体平台 V2 测试大纲

> 状态：**已审核确认，入项目 wiki**（2026-11-06）｜ 依据：《V2-功能需求描述》（已确认入 wiki，2026-11-06 基线）｜ 回归基线：MVP v1.0.2
> 用途：明确 V2 项目测试点（TP），作为测试用例生成的输入。编号规则：TP-<需求编号>-<序号>，如 V2-01 → TP-01-xx。
> 测试点类型：功能 / 负向 / 安全 / 性能 / 故障演练 / 评估。优先级：P0=发布阻断、P1=核心验收、P2=完整验收。

## 一、测试范围

- **范围内**：V2-01~V2-21 全部需求的功能验收、跨需求架构不变式、性能基准、安全负向、故障演练。
- **范围外**：需求文档未列入的非功能待办（L6 数据回填、提交门禁）；外部业务系统内部逻辑；AI 平台（LLM 消费方）自身质量。
- **核心目标**：① 逐条验证 21 项需求验收条款；② 验证贯穿全局的**架构不变式**（第二章，最高优先级）；③ MVP v1.0.2 回归不破坏。

## 二、架构不变式横切测试（跨需求，P0）

以下不变式必须**在所有相关渠道**上成立，是本项目测试的核心：

| 编号 | 不变式 | 验证方法（含负向断言） |
|---|---|---|
| INV-1 | **实例数据模型**：源连接型值不落地（只存关系快照：stable_key/类型/关系边/治理元数据），上传型值落地平台侧 | 平台存储 dump 断言：源连接型实例无非键内容值；快照字段完整；上传型值可本地读取 |
| INV-2 | **实例永不共享**：共享只授 schema 只读；源连接内容由源系统按访问者权限决定（同一本体不同访问者返回范围不同）；上传型默认仅上传者可读、显式开放、上限=共享等级可见范围、可收回留审计 | 租户/共享等级×渠道矩阵遍历；开放前后读权限断言；审计留痕断言 |
| INV-3 | **AI 只在构建侧、不在执行侧**：执行路径可复现可审计；编排页无代码入口（UI＋API 双负向）；LLM 不参与运行时分支决策/工具选择/参数填充 | 同一触发多次执行路径一致断言；API 传代码字段被拒断言；生成物结构化校验 |
| INV-4 | **审计不可篡改**：全量操作 who/when/what/前后值，不可经 API 修改/删除 | 各操作后审计检索；篡改/删除负向测试 |
| INV-5 | **版本引用机制统一**：融合本体版本（V2-02）与 schema 版本（V2-07）消费方可固定引用、旧版可用 | 固定引用读取断言；未指定默认最新稳定版断言 |
| INV-6 | **外部对接统一 MCP**：无 JDBC/SQL 直连适配器 | 接口负向：数据库直连类接口不存在 |

## 三、测试策略

1. **分层**：L1 接口契约（422/403/404 语义、元模型校验）→ L2 功能 E2E（需求正常流＋验收条款）→ L3 集成（mock MCP、身份联邦、CDC、K8s）→ L4 非功能（性能/安全/故障演练）→ L5 回归（MVP 基线）。
2. **与实施批次联动**：按需求文档"建议实施顺序"四批次，每批次完成后过一次 L5 回归门禁再进下一批。
3. **用例生成规则**：每个 TP 为用例最小单元；各需求"正常流"直接作为 E2E 用例骨架（前置＝数据准备、步骤＝操作序列、预期＝断言）；验收条款逐条落断言。E2E 用例按**入口渠道**拆三类：浏览器 UI、开放接口（REST/GraphQL/SPARQL）、MCP（外部 AI 平台为发起方），核心主链路须各有一条从真实入口完整执行的用例（见第五章"入口渠道完整流"）。**每个 EP（第六章）独立转负向/故障用例**，断言焦点是"失败是否正确"（正确拒绝语义、不静默漏过、不产脏数据、告警发出、审计留痕、可恢复）；同一需求的正常流与异常流用例须同时覆盖。
4. **golden dataset 前置**：V2-14 生成类能力（SOP/skill→草稿、AI 局部生成）验收前，必须先构建并冻结 golden dataset（四类样本：多分支/能力缺口/高风险步骤/干扰项；指标阈值测试前冻结），不得仅以"编排能跑通"判定通过。

## 六、异常流测试点（Abnormal Flows，EP）

> 与第五章关系：TP 是**验收主线**（正常流＋条款断言）；EP 是**失败路径主线**——系统遇到失败、被拒、边界情形时的行为验证。断言焦点："失败是否正确"（正确拒绝、显式报错不静默、无脏数据/脏关系入快照、告警发出、审计留痕、可恢复）。EP 与已有 TP 重复的场景不重复列（标注"见 TP-xx-xx"）。用例生成：EP 逐个转负向/故障用例，故障类需可注入（mock MCP/混沌手段）。

## 七、权限与安全专项矩阵

1. **RBAC×资源矩阵**：管理员/建模人/审核人/只读 × 项目/本体/实例/字典/审批的读写访问，逐格断言（TP-05/09 覆盖点展开）。
2. **租户×共享等级×渠道矩阵**（INV-2 核心）：私有/项目组/部门/公开 × schema 读 / 源连接内容读 / 上传型内容读 / 写操作，逐格断言。
3. **凭据安全**：身份联邦凭据加密存储；日志/审计/报错信息中无凭据明文（grep 负向断言）。
4. **注入与越权**：MCP/REST/GraphQL/SPARQL 未鉴权与越权负向；SPARQL 注入（跨命名图访问）负向。
5. **审计完整性**：上述安全测试中的每次越权尝试本身也须产生审计记录（攻击留痕）。

## 十、需求覆盖追溯

- 追溯方式：各测试点表"依据"列即映射（需求条款/验收条款编号/正常流步骤），测试点 ID 可在用例与缺陷中双向引用。
- 覆盖要求：21 项需求每项至少 1 个 P0 测试点；每条验收条款至少 1 个测试点；INV-1~6 各需求相关渠道均被对应 TP 覆盖（INV 表为横切索引）；**正常流与异常流双线覆盖**：每项需求至少 1 个 TP＋1 个 EP，确无异常场景的需求须在测试设计评审时显式记录理由。
- 缺口管理：测试设计评审时逐条核对验收条款→TP，未覆盖条款须补 TP 或显式记录豁免理由。
