### 1.2 校验结果

按本体逐条校验 `unique` / 必填 / `data_type` / `pattern` / `min-max` / `enum`，**只发现 1 处问题**：

> **`obj_material` 的 unique 约束建错了键。**

- 现状：`cst_u_material` 建在 `attr_pn`（物料 PN）上，但 **PN 不是唯一键**——同一个 PN 在**两个工厂（1100 / 1600）下各有一条，单价不同**（例：`V00202Y000000000` 在 1100 厂 = 100.0，在 1600 厂 = 144.0）。
- 实测：93 条物料中 **37 个 PN 重复**（74 条），而真正的业务主键 `attr_material_code`（工厂-PN 复合，**93 条零重复**）。
- 对象的 `stable_key` 已经是 `attr_material_code`，**约束与主键不一致**。

**修复建议（一行改动）**：把 `cst_u_material` 的 `params.attribute` 从 `attr_pn` 改为 `attr_material_code`，名称改为「物料编码唯一」。

> ⚠️ 修复后 SHACL 不再误报，但**按 PN 查单价仍会命中 2 条**——这是业务事实，不是 bug。因此未来 `lookup(物料, …)` **必须带工厂维度**或用 `material_code` 定位，否则必然触发 `AMBIGUOUS`。

其余 **16 条 unique 约束全部 0 重复**，与 `stable_key` 完全一致。

### 1.3 空值定性（不是缺陷，但影响 lookup）

| 对象 | 属性 | 空值 | 定性 |
|---|---|---|---|
| 售后人工基线 | `attr_customer` | 1132（海外 100%） | 源表「售后人工成本基线（海外)」**没有客户列**，属材料结构，非导入遗漏 |
| 实施人工基线 | `attr_customer` / `attr_model` | 224 / 216 | 同上 |

**关键结论：国内与海外的维度组合不同，lookup 必须分叉**

- 国内：`U数 × 客户 × 产品类别 × 响应等级`（无区域）
- 海外：`U数 × 区域 × 产品类别 × 响应等级`（无客户，25 个国家/地区）

若用统一维度匹配，海外 1132 条会塌成 48 组重复 → 必然 `AMBIGUOUS`。这验证了能力层设计中「维度匹配必须显式声明」的必要性。

## 二、成本清单复算（33 行）

### 2.1 口径（来自《成本核算说明》权威原文）

| 项 | 公式 |
|---|---|
| E 人工成本 | `E = 现场服务率 D × 单台人工成本基线 C` |
| K 备件辅助 | 国内 `K = H × G`；海外 `K = H×G + I×J×1.1×1.02` |
| N 管理成本 | `N = 管理成本基线 L × 现场服务率 M` |
| O 成本合计 | `O = E + F + K + N` |
| S 成本占比 | `S = O / R` |
| 年限上浮 | `D4 = D3 + D3/3×1.2`（1.4）；`D5 = D3 + D3/3×1.2 + D3/3×1.2×1.2`（1.88） |
| F 备件直接 | BOM 逐部件 `Σ(数量×单价×故障率)`；4H×1.15；介质保留走不返还；海外 ARMA/RMA 组合口径 —— **本轮不重算，引用主表原值并标注** |

所有基线值**全部经 `lookup()` 从本体实例取**，未硬编码常量；命中 0 条报 `NOT_FOUND`、多条报 `AMBIGUOUS`，不静默取首条（与《能力层元模型设计》§5 一致）。

### 2.2 复算结果

**一致 87 项，不一致 36 项，且 36 项 100% 归因于同一个原因。**

> 数字较初版（83/28）增加，是因为补上了 ARMA/RMA 行：这类行源表 `C` 为空、`E = 0`，
> 合计 `O = F + K + N`。修正 `O` 的成立条件后，`r19/r20/r22/r23` 的合计与占比也进入了可校验范围。

> **发现：主表海外四年/五年的现场服务率，上浮基数未按区域分叉。**

- 海外三年 `D3 = 0.215653093423419`（OR-010），按公式四年应为 `0.2156530934 × 1.4 = 0.3019143308`
- 主表实际写 `0.306453599013611` = **国内** D3 `0.218895427866865 × 1.4`

即主表在四年/五年行统一用了国内 D3 作基数（疑似绝对引用了国内基准单元格），而三年行用的是本区域的 D3。

**受影响行**：`r19 / r20 / r22 / r23 / r25 / r26 / r28 / r29`（全部为欧洲德国的四年/五年行）。
**国内 25 行全部吻合。**

**影响量化**：以 r25（欧洲德国 四年5×9×NBD现场）为例，源表 O = 939.3472，按区域口径应为 925.9461，**每台多算约 13.4 元（1.5%）**。

**建议与业务确认**：海外四年/五年的现场服务率应以哪个 D3 为上浮基数。这是材料口径问题，不是平台问题——但正因如此，才更需要在平台里把公式显式定义下来（写进能力层后，这类不一致会在定义时暴露，而不是藏在 Excel 单元格引用里）。

### 2.4 MOCK 口径（业务确认前的临时基准）

材料未给出海外四年/五年应以哪个 D3 为上浮基数。**在业务确认前，本清单按 MOCK 口径出数**：

```
D_mock = 同区域三年实测 D3 × 年限系数    （四年 1.4 / 五年 1.88）
基数    = 0.215653093423419             （OR-010.attr_onsite_rate，与主表海外三年行 D 完全一致）
D_mock(四年) = 0.3019143307927866
D_mock(五年) = 0.4054278156360277
```

**MOCK 三法校验（三者结果一致，互为验证）**：

| 方法 | 算式 | 四年结果 |
|---|---|---|
| 法1 区域 D3 × 系数 | `0.2156530934 × 1.4` | 0.3019143308 |
| 法2 主表 D × 区域比 | `0.3064535990 × (0.2156530934 / 0.2188954279)` | 0.3019143308 |
| 法3 主表海外三年 D × 系数 | `0.2156530934 × 1.4` | 0.3019143308 |

法2 与法1 等价，说明 MOCK 值等价于"按区域三年实测比值对主表值做等比缩放"，不是凭空凑数。

**影响量化（8 行合计）**：源表 O 合计 7970.69 元 → MOCK 口径 7858.20 元，**差 112.50 元（1.43%）**，源表偏高。
逐行差额 1.38% ~ 1.47%，分布均匀，无异常行。

**golden dataset 因此分为三级**（已写入 Excel「Golden Dataset说明」Sheet）：

| 层级 | 范围 | 用途 |
|---|---|---|
| **L1 硬基准** | 国内 25 行 + 海外三年行，87 项一致、0 差异 | 引擎上线后**必须逐项复现**，否则判定引擎有缺陷 |
| **L2 软基准** | 欧洲四年/五年 8 行的 D 及派生项，36 项 | 待业务确认后升为 L1，或按业务口径替换 |
| **L3 未覆盖** | F 备件直接成本（33 行） | 依赖整机 BOM 逐部件聚合，本体未建模，当前引用主表原值 |

## 三、MCP 对照实验：没有公式时，Agent 能算对吗

### 3.1 硬证据：MCP 给不出任何公式

```
Ontology.functions = []        # 实测本体文件，公式数量为 0
ontology_query -> 17 对象 / 89 属性 / 2 关系 / 17 约束
instance_get   -> 2297 条实例
```

本体中**没有任何一处**描述「E = C × D」这样的计算关系。

补充实测：`GET /api/mcp/server/tools` 返回 4 个工具（`ontology_query` / `inference_trace` / `instance_get` / `action_invoke`），**无计算类工具**——这一点成立。

> **【结论更正 · 2026-10-28】** 本节原写"`tools/call` 链路当前不通"，**该判断错误**，是我用错了传输协议：
> 我按 Streamable HTTP 的姿势 `POST /mcp/{project_id}`，而平台只实现了 SSE 传输（MCP 2024-11-05），故返回 405。
> 改用正确姿势实测，**链路完全可用**：`GET /mcp/{pid}` 拿到 endpoint → `POST` 该 endpoint `initialize`
> （回 2024-11-05）→ `tools/list` 列出 4 工具 → `tools/call ontology_query` / `instance_get` 均正常返回数据。
> 真实缺口是"只支持旧传输 + 几处治理缺口"，已另立
> 《[平台修改建议 · MCP 接入层修复](平台修改建议-MCP接入层修复.md)》。
> 本节"本体中没有公式"的**核心结论不受影响**——MCP 能通，但通了也拿不到任何公式。

### 3.2 仅凭数据，各公式的「可反推性」实测

检验 `ans / (a × b)` 是否恒等于 1：

| 公式 | 命中行 | 不成立 | 最大偏差 | 判定 |
|---|---:|---:|---:|---|
| `E = C×D` | 15 | 0 | 0.0000 | 形式上可反推 |
| `K = G×H`（国内） | 9 | 0 | 0.0000 | 形式上可反推 |
| `K = G×H`（海外） | 12 | 0 | 0.0000 | 碰巧成立，见下 |
| `N = L×M` | 21 | 0 | 0.0000 | 形式上可反推 |
| `S = O/R` | 33 | 0 | 0.0000 | 形式上可反推 |
| `D4/D5` | — | — | — | 比值 1.4 / 1.88 可算，**来源不可知** |
| `F` | — | — | — | **完全不可反推** |

**海外 K 的陷阱**：公式实为 `K = H×G + I×J×1.1×1.02`，但本例 `I` 全为 0，残差恒为 0——Agent 反推出的 `K = G×H` **在数据里碰巧全对**，一旦出现非零 `I` 就会错。隐藏的税/保险系数 `1.1×1.02` 在数据中**不可见**。

### 3.3 结论：可反推 ≠ 可用

| 公式 | 数据可反推 | Agent 能可靠使用吗 |
|---|---|---|
| `E = C×D` | 是 | 否：不知道介质保留行不适用 |
| `K = G×H` | 国内是 / 海外碰巧 | 否：海外隐藏系数不可见 |
| `N = L×M` | 是 | 否：需先知道 L 取哪条基线（维度组合） |
| `O = E+F+K+N` | 是 | 否：F 算不出来 |
| `D4/D5 上浮` | 数值可算 | 否：来源不可知，**无法外推到第 6 年** |
| `F 备件直接` | 完全不能 | 否：缺 BOM 明细建模 |

> **一句话**：数据能让 Agent「猜对」简单乘积，但每一次「猜对」都缺少**适用范围、边界条件与隐藏系数**。这正是能力层要解决的问题，也是本项目作为语义底座的价值兑现点。
