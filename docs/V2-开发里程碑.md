## 一、开发范式（与 MVP 一致）

1. **按需求垂直验证**：每个切片 = 一项功能需求，走完整「前端 UI → 后端 API → 存储/外部系统」链路，可独立 E2E 测试；退出标准 = 该需求 P0 测试点（大纲 TP-xx-yy）全绿 + 所属 E2E 检查点通过。
2. **不分层**：不存在"先全部后端接口、再统一做 UI"的阶段；每个切片自带前端入口、后端实现、mock 集成与测试脚本。
3. **测试点驱动验收**：测试点→用例→脚本三级映射（用例见 `docs/V2-测试用例.md`，TC↔TP、TCE↔EP 一一对应）；测试脚本开发后，在项目 wiki《V2-测试用例》页对应条目登记脚本链接。
4. **依赖显式化**：跨需求依赖只允许两种解法——调整切片顺序，或拆出独立前置切片（见 §六 偏差决策 D1/D2）。
5. **回归保护**：每个里程碑退出跑 L5 全量回归 + 本里程碑 E2E 检查点；不变式（INV-1~6）随相关切片逐步验证，终验全矩阵（见 §五）。

### M2-A ✅ ｜ V2-05 登录鉴权 + RBAC（P0，2026-11-11 完成：验收 67/67，L5 回归 93/93）

- **垂直链路（已落地）**：登录页（httpOnly Cookie 会话）→ JWT（过期/篡改/登出撤销 401）→ 后端全局鉴权过滤器（未登录 401/无权限 403）→ RBAC（4 角色＋资源级授权到项目/本体粒度）→ 前端菜单/操作入口权限矩阵（越权隐藏或禁用）→ 角色调整即时生效（免重登）→ 密码错误/账号不存在统一文案（防枚举）＋ 5 次失败锁定 → SSO 预留接口（存在但不启用）→ 授权/越权审计。
- **关键决策**：① 按 INV-3 之外的新增约束，JWT **只带身份、不带权限**，每次请求实时查库，故角色调整免重登且过期 token 不残留权限；② 全局过滤器只覆盖 `/api/*` 与页面，`/mcp/*` 沿用项目静态 token 独立体系，且不改 `main.py` 中间件层级（避免 M1-B legacy SSE 双响应复发）；③ `ONTOLOGY_AUTH_ENABLED=false` 仅作 L5/M1 回归的测试态豁免，默认启用、生产严禁设置，M2-A 验收在启用态进行。
- **验收**：`scripts/verify_m2a_auth_rbac.py` **PASS=67/FAIL=0/SKIP=0**，覆盖 TP-05-01~05 / EP-05-01~03（8 点）＋ TC/TCE-05 边界＋真实 Chromium DOM 登录与权限矩阵＋MCP 体系不受影响＋默认启用断言。
