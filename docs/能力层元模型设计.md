# 能力层元模型设计（Capability Layer Metamodel）

> 定位：本文档是《平台修改建议-计算能力与公式引擎》第八节"通用性评估"的落地设计。
> 目标：把"公式引擎"升级为**与业务领域无关的能力层**——先定义抽象元模型，再由不同本体按需实例化。
> 读者：平台开发（后端/前端）、本体建模人员。
> 状态：设计稿 v0.1，尚未实现；平台当前 `OntologyFunction` 为空壳元模型（无引擎、无 API、无 UI）。

---

## 0. 适用范围

**在范围内**
- 派生值的生产与执行（数值、文本、枚举、日期、布尔、引用）
- 跨实例校验与勾稽（SHACL 表达不了的部分）
- 条件触发与受控副作用（复用现有 Action）
- 执行结果的溯源、审计与版本治理

**不在范围内**（明确排除，见 §10）
- 长事务 / 多步人工工作流编排
- 外部连接器治理（凭据、限流、重试策略）
- 非确定性求值（LLM 参与判断，默认不提供）

---

## 1. 设计原则

| 原则 | 含义 |
|---|---|
| **抽象优先** | 先有元模型与运行时，再有具体能力。成本公式是一个实例，不是引擎本身 |
| **核心 / 场景分离** | 与领域无关的进核心；单位、精度、币种等进 `domain_ext` 扩展包 |
| **语义与实现正交** | `kind`（产出什么）× `implementation`（怎么算）独立变化 |
| **向后兼容** | 现有 `OntologyFunction` / `OntologyConstraint` / `Action` 均可平滑映射，不废弃 |
| **确定性默认** | 默认纯函数、可重放；非确定性必须显式声明并强制人工确认 |
| **可溯源** | 任何执行结果必须能回溯到「能力版本 + 输入实例 + 输入属性 + 输入原值」 |

## 2. 元模型总览

```
Ontology
├── objects[]          （已有）
├── constraints[]      （已有，rule 当前支持 "unique"）
├── functions[]        （现有空壳，迁移为 capabilities 的特例）
├── actions            （已有，外部回写）
└── capabilities[]     ★ 新增
```

**能力（Capability）** = 一个有签名、有实现、有执行契约的**可执行语义单元**。

两个正交维度：

- **`kind`**（语义）：`derive` | `assert` | `act`
- **`implementation`**（实现）：`expression` | `decision_table` | `script` | `external`

`kind` 与 `implementation` 构成 3 × 4 矩阵，格子的组合是否提供由 §3.4 的执行契约决定（例如 `act × expression` 刻意不提供）。

## 3. 完整字段定义

### 3.1 CapabilityDefinition（核心定义）

| 字段 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `capability_id` | string | ✅ | — | 稳定标识，建议前缀 `cap_`（对齐 `obj_/attr_/rel_`）；迁移期兼容 `fn_` |
| `name` | string | ✅ | — | 业务可读名称，如"维保服务产品成本核算" |
| `business_definition` | string | ✅ | — | 一句话说明这个能力做什么、边界在哪（对齐对象 `business_definition` 必填约定，≥5 字符） |
| `version` | string | ✅ | `"1"` | 语义版本；基线或公式变更须升版，旧版本结果可追溯 |
| `kind` | enum | ✅ | — | `derive` \| `assert` \| `act` |
| `signature` | object | ✅ | — | 输入/输出签名，见 §3.2 |
| `implementation` | object | ✅ | — | 实现体，见 §3.3 |
| `effects` | enum | ✅ | `pure` | `pure` \| `read` \| `write`，见 §3.4 |
| `deterministic` | bool | — | `true` | 为 `false` 时强制 `confirmation=human_required` 且全量审计 |
| `idempotent` | bool | — | `true` | 仅对 `effects=write` 有意义；`false` 时重放需显式确认 |
| `triggers` | Trigger[] | — | `[]` | 触发条件，见 §3.5 |
| `depends_on` | string[] | — | `[]` | 依赖的其他 capability_id；用于拓扑排序与影响分析，禁止环 |
| `domain_ext` | object | — | `{}` | 场景专属扩展包，见 §3.6 |
| `status` | enum | ✅ | `draft` | `draft` \| `active`；**仅 `active` 可被执行与共享**，随本体发布（见 §12.4） |
| `visibility` | enum | — | `private` | `private`（仅本体内）/ `project`（同项目跨本体可引用）/ `shared`（跨项目）；**仅 `status=active` 时生效** |
| `enabled` | bool | — | `true` | 停用后不可执行，但保留历史结果可追溯 |
| `created_at` / `updated_at` | string | — | — | ISO8601，与现有存储一致 |

### 3.2 Signature（签名）

```jsonc
"signature": {
  "inputs": [
    { "name": "product_code", "type": "string",  "required": true,  "source": "param" },
    { "name": "region",       "type": "enum",    "required": true,  "source": "param" },
    { "name": "整机成本",      "type": "number",  "required": false, "source": "attribute", "ref": "attr_machine_cost" }
  ],
  "output": { "type": "number", "nullable": false }
}
```

| 字段 | 说明 |
|---|---|
| `name` | 参数名；表达式中直接引用 |
| `type` | 见 §4 值类型系统 |
| `required` | 缺失时报错 `MISSING_INPUT` |
| `source` | `param`（调用方传入）/ `attribute`（从当前实例属性取）/ `resolved`（由引用解析得到，如 lookup 结果） |
| `ref` | `source=attribute` 时对应的属性 id |
| `default` | 可选默认值（**建议少用**，易掩盖数据缺失，与"lookup 未命中不得补默认值"原则冲突） |

`assert` 类的 `output.type` 恒为 `boolean`，并额外返回 `evidence`（证据链）。

### 3.3 Implementation（实现体）

四选一，由 `kind` 字段区分。

**(a) expression**

```jsonc
"implementation": {
  "kind": "expression",
  "language": "opl-expr/v1",
  "body": "E = lookup(obj_labor_baseline, {维度}, \"MA成本基线\") * service_rate\nO = E + F + K + N",
  "options": { "strict_types": true, "null_propagation": "error" }
}
```

| 字段 | 说明 |
|---|---|
| `language` | 方言标识，预留演进（`opl-expr/v1` 为首个版本） |
| `body` | 表达式正文，支持多行顺序绑定，最后一行为返回值 |
| `options.strict_types` | 类型不匹配报错而非隐式转换 |
| `options.null_propagation` | `error`（默认，空值参与运算即报 `NULL_INPUT`）/ `propagate`（结果置空） |

**(b) decision_table**

```jsonc
"implementation": {
  "kind": "decision_table",
  "hit_policy": "unique",            // unique | first | priority | collect
  "inputs":  [{ "name": "运行时长", "type": "number" }, { "name": "故障等级", "type": "enum" }],
  "outputs": [{ "name": "服务等级", "type": "enum" },    { "name": "响应时限", "type": "duration" }],
  "rules": [
    { "when": [">= 8760", "\"P1\""], "then": ["\"金牌\"", "\"2h\""], "note": "连续运行一年以上且一级故障" }
  ],
  "default_output": ["\"标准\"", "\"8h\""]
}
```

| 字段 | 说明 |
|---|---|
| `hit_policy` | `unique` 要求命中且仅命中一条；`first` 取首条；`priority` 按 `priority` 字段；`collect` 返回列表 |
| `rules[].when` | 每格为表达式字符串，空字符串表示"不关心" |
| `rules[].then` | 输出值表达式 |
| `default_output` | 无命中时的输出；不填且无命中 → 报 `NO_MATCH` |

**(c) script（沙箱，P2 —— 已决议延后，见 §12.2）**

```jsonc
"implementation": {
  "kind": "script",
  "language": "python",
  "entry": "solve",
  "body": "def solve(ctx):\n    ...",
  "sandbox": { "timeout_ms": 2000, "memory_mb": 128, "allowed_modules": ["math", "datetime"], "no_network": true },
  "reviewed": false
}
```

| 字段 | 说明 |
|---|---|
| `sandbox.no_network` | 恒 `true`，脚本不得外联 |
| `allowed_modules` | 白名单，禁止 `os / subprocess / socket / requests` |
| `reviewed` | 需人工评审标记；未评审的脚本**不可在 `effects=write` 下执行** |

**(d) external**

```jsonc
"implementation": {
  "kind": "external",
  "action_id": "act_erp_sync",       // 复用现有 Action 定义
  "input_map": { "order_no": "expr: this.订单编码", "amount": "expr: O" }
}
```

| 字段 | 说明 |
|---|---|
| `action_id` | 指向现有 Action，复用其 `target_connection / invoke / idempotency_key / confirmation` |
| `input_map` | 值支持 `expr:` 前缀表示用表达式求值，否则为字面量 |

**(e) composition（能力组合，P1 提供）**

`act` 类禁用 `script` 后，复杂动作通过**组合**而非脚本实现：把判断、路由、入参计算拆成独立的 pure 能力，再由 act 能力按顺序编排。

```jsonc
"implementation": {
  "kind": "external",
  "action_id": "act_erp_approval",
  "pipeline": [
    { "capability_id": "cap_cost_reconcile", "as": "reconciled", "on_false": "abort" },  // assert：前置校验
    { "capability_id": "cap_approver_pick",  "as": "approver" },                          // decision_table：路由
    { "capability_id": "cap_payload_build",  "as": "payload" }                            // expression：入参构造
  ],
  "input_map": { "approver": "ctx.approver", "payload": "ctx.payload" }
}
```

| 字段 | 说明 |
|---|---|
| `pipeline[]` | 顺序执行的 pure 能力，共享上下文 `ctx` 与同一 `trace_id` |
| `as` | 结果在上下文中的名字，供后续步骤与 `input_map` 引用 |
| `on_false` | 仅对 `assert` 类步骤有效；`abort`（默认，终止且不产生副作用）/ `continue` |

约束：`pipeline` 内的能力**必须全部为 `effects=pure`**；副作用只能由 `action_id` 产生。这样"复杂逻辑"与"副作用"的边界在结构上被强制分离。

### 3.4 effects 与执行契约

| effects | 语义 | 约束 |
|---|---|---|
| `pure` | 无副作用，只依赖输入与本体数据 | 可缓存、可重放、可并发；**默认** |
| `read` | 会读取外部系统（如查外部定价） | 记录外部读取；结果可缓存但需标注来源与时效 |
| `write` | 会产生外部写 | 必须走 Action 两段式（execute → `confirmation_token` → confirm）；必须提供 `idempotency_key`；默认 `confirmation=human_required` |

组合约束（**不满足即拒绝保存**）：

| kind | 允许的 effects | 常用 implementation |
|---|---|---|
| `derive` | `pure`（可 `read`） | expression / decision_table / script / external |
| `assert` | `pure`（可 `read`） | expression / decision_table / external |
| `act` | `write` | external（**不允许 expression 直接产生副作用**） |

### 3.5 Trigger（触发与条件）

```jsonc
"triggers": [
  {
    "event": "instance.updated",          // 见下表
    "scope": { "object_type": "obj_maintenance_product" },
    "when": "this.状态 == \"已发布\" and O > 0",
    "mode": "sync",                        // sync | async
    "on_failure": "log"                    // log | block | rollback
  }
]
```

| `event` 取值 | 说明 |
|---|---|
| `instance.created` / `instance.updated` | 实例创建/更新（导入审批通过后视为 created） |
| `instance.approved` | 候选实例审批入库 |
| `schedule` | 定时（需配 `cron`，建议 P2 提供） |
| `mcp_call` | 被 MCP `capability_call` 调用 |
| `manual` | 人工在 UI 触发（**默认必开**） |

| `on_failure` | 说明 |
|---|---|
| `log` | 记录失败，不影响主流程（默认） |
| `block` | 阻断触发它的操作（如校验不通过则不允许入库） |
| `rollback` | 回滚同批次的 write（仅对 `effects=write` 且已声明幂等键时可提供） |

### 3.6 domain_ext（场景扩展包）

核心元模型**不含**领域专属字段，一律放 `domain_ext`，由平台按 key 做可选校验。

已定义的扩展包：

| 包名 | 字段 | 适用 |
|---|---|---|
| `numeric` | `unit`（元/小时/次/%）、`precision`（小数位）、`rounding`（`half_up`/`half_even`/`none`）、`currency` | 数值类 `derive` |
| `quality` | `confidence`（置信度）、`evidence_required`（是否必须附证据） | `assert` 类校验 |

```jsonc
"domain_ext": {
  "numeric": { "unit": "元", "precision": 4, "rounding": "half_up", "currency": "CNY" }
}
```

新增扩展包 = 在平台注册一个 schema（可选校验器），**不改核心元模型**。这正是"抽象优先"的收益点。

## 4. 值类型系统

对齐本体 `data_type` 并扩展：

| 能力层类型 | 说明 | 对应本体 data_type | 备注 |
|---|---|---|---|
| `number` | 数值（含整数与浮点） | `integer` / `float` | 精度由 `domain_ext.numeric` 控制 |
| `string` | 文本 | `string` | |
| `boolean` | 布尔 | `boolean` | `assert` 的输出恒为此 |
| `date` | 日期 | `date` | |
| `datetime` | 日期时间 | `datetime` | |
| `duration` | 时长（如"2h""3d"） | — | 能力层新增，便于 SLA/期限计算 |
| `enum` | 枚举（显式化为类型） | `string` + `constraints.enum` | 取值必须在白名单内 |
| `ref` | 指向某个实例的引用 | 关系字段 | 可继续导航 `.attr` |
| `list<T>` | 同型集合 | 关系的 many 侧 | 支持 `sum/count/avg/min/max/filter/map` |
| `object` | 结构化输出（多字段） | — | 仅用于 `derive` 的输出（如一次返回成本明细） |

## 5. 引用与解析（Resolution）

表达式中取值的四种路径：

| 形式 | 示例 | 语义 |
|---|---|---|
| 本实例属性 | `this.整机成本` | 取当前实例属性 |
| 关系导航 | `this.适用区域.税率` | 沿关系取（many 侧得到 `list`） |
| 主键定位 | `obj_region[编码 == "国内"].税率` | 按属性值定位唯一实例 |
| 维度匹配 | `lookup(obj_labor_baseline, {U数: this.U数, 客户: this.客户}, "MA成本基线")` | 按多维组合定位 |

**强制语义**（沿用既有教训）：

- `lookup` / 主键定位命中 **0 条 → `NOT_FOUND`**；命中 **多条 → `AMBIGUOUS`**。**禁止静默取首条、禁止补默认值。**
- 关系导航到 many 侧若直接当标量用 → `TYPE_MISMATCH`，须先聚合。

错误码总表：

| 错误码 | 触发 |
|---|---|
| `NOT_FOUND` | 引用目标不存在 |
| `AMBIGUOUS` | 定位命中多条 |
| `MISSING_INPUT` | 必填输入缺失 |
| `NULL_INPUT` | 空值参与运算且 `null_propagation=error` |
| `TYPE_MISMATCH` | 类型不匹配（含标量/集合混用） |
| `UNIT_MISMATCH` | `domain_ext.numeric` 已声明单位时量纲冲突 |
| `DIV_ZERO` | 除零 |
| `NO_MATCH` | 决策表无命中且无 `default_output` |
| `EVAL_ERROR` | 表达式语法/求值错误（含子表达式位置） |
| `TIMEOUT` | script 或 external 超时 |
| `FORBIDDEN_EFFECT` | 组合约束不满足（如 `act × expression`） |
| `DEPENDENCY_CYCLE` | `depends_on` 成环 |

## 6. 执行运行时契约

### 6.1 执行请求

```jsonc
POST /api/ontologies/{ontology_id}/capabilities/{capability_id}/execute
{
  "bindings": { "product_code": "SA-001", "region": "国内" },
  "instance_id": "inst_xxx",        // 可选：以某实例为 this
  "dry_run": true,                  // 默认 true
  "include_trace": true
}
```

批量：`POST .../execute-batch`，`bindings` 为数组，返回结果集（对应"生成成本 list"）。

### 6.2 执行响应

```jsonc
{
  "capability_id": "cap_maintenance_cost",
  "version": "1",
  "dry_run": true,
  "output": { "E": 45.5829, "O": 209.8305, "S": 0.0055699 },
  "trace": [
    { "step": "service_rate", "expr": "lookup(...)", "value": 0.2188954,
      "sources": [{ "instance_id": "OR-009", "object_type": "obj_region", "attribute_id": "attr_onsite_rate", "value": 0.2188954 }] },
    { "step": "E", "expr": "C * D", "value": 45.5829,
      "sources": [
        { "instance_id": "AL-DOM-065", "object_type": "obj_impl_labor_baseline", "attribute_id": "attr_ma_baseline", "value": 208.2404 },
        { "instance_id": "OR-009",     "object_type": "obj_region",             "attribute_id": "attr_onsite_rate", "value": 0.2188954 }
      ] }
  ],
  "warnings": [],
  "errors": []
}
```

`trace[].sources` 是**溯源的强制字段**——没有 sources 的输出视为不合规实现。

### 6.3 通用执行约束

- **默认 `dry_run=true`**：不写任何数据；`effects=write` 必须显式 `dry_run=false` 并携带确认令牌。
- **幂等**：`effects=write` 必须提供 `idempotency_key`（复用 Action 现有机制）。
- **批量原子性**：建议与实例导入一致（整批成功或整批回滚），避免半批落库。
- **MCP 暴露**：新增 `capability_call`（`side_effect` 由 `effects` 推导），让 Agent 调平台算而不是自己算。

## 7. 三个不同领域的实例化样例

> 三个样例分别覆盖：数值计算 / 枚举判定与状态迁移 / 触发与副作用，恰好落在矩阵的不同格子。

### 7.1 领域一 · 服务成本（财务域）—— `derive × expression`

**背景**：维保服务产品成本模型（本项目，17 对象 / 2297 实例）。

```jsonc
{
  "capability_id": "cap_maintenance_cost",
  "name": "维保服务产品成本核算",
  "business_definition": "按区域与现场服务率，从各成本基线计算维保服务产品的各项成本、合计与整机占比",
  "version": "1",
  "kind": "derive",
  "signature": {
    "inputs": [
      { "name": "region",   "type": "enum",   "required": true, "source": "param" },
      { "name": "整机成本",  "type": "number", "required": true, "source": "attribute", "ref": "attr_machine_cost" }
    ],
    "output": { "type": "object" }
  },
  "implementation": {
    "kind": "expression",
    "language": "opl-expr/v1",
    "body": "C = lookup(obj_labor_baseline,  {区域: region}, \"MA成本基线\")\nD = lookup(obj_region, {区域: region}, \"现场服务率\")\nE = C * D\nF = sum(this.配置部件.map(p => p.单价 * p.故障率))\nG = lookup(obj_material, {区域: region}, \"辅助成本基线\")\nK = G * D\nL = lookup(obj_manage_baseline, {区域: region}, \"管理成本基线\")\nN = L * D\nO = E + F + K + N\nS = O / this.整机成本\n{ E: E, F: F, K: K, N: N, O: O, S: S }"
  },
  "effects": "pure",
  "deterministic": true,
  "depends_on": [],
  "domain_ext": { "numeric": { "unit": "元", "precision": 4, "rounding": "half_up", "currency": "CNY" } }
}
```

校验基准（主表 r3 国内行）：`E = 208.2404 × 0.2188954 = 45.5829`；`K = 19.4257`；`N = 127.7403`；`O = 209.8305`；`S = 209.8305 / 37672 = 0.0055699`。

配套 `assert` 能力（勾稽，`assert × expression`）：

```jsonc
{
  "capability_id": "cap_cost_reconcile",
  "kind": "assert",
  "signature": { "output": { "type": "boolean" } },
  "implementation": {
    "kind": "expression",
    "body": "abs(this.成本合计 - (this.MA人工成本 + this.备件直接成本 + this.备件辅助成本 + this.管理成本)) < 0.0001"
  },
  "effects": "pure"
}
```

### 7.2 领域二 · 设备运维服务等级（制造/运维域）—— `derive × decision_table`

**背景**：完全不同的本体——设备台账、故障工单、SLA 策略。无数值计算，产出是**枚举与时长**。

```jsonc
{
  "capability_id": "cap_service_level",
  "name": "设备服务等级与响应时限判定",
  "business_definition": "依据设备连续运行时长、近 90 天故障次数与故障等级，判定服务等级与响应时限",
  "version": "1",
  "kind": "derive",
  "signature": {
    "inputs": [
      { "name": "运行时长",   "type": "duration", "required": true, "source": "attribute" },
      { "name": "故障次数",   "type": "number",   "required": true, "source": "attribute" },
      { "name": "故障等级",   "type": "enum",     "required": true, "source": "attribute" }
    ],
    "output": { "type": "object" }
  },
  "implementation": {
    "kind": "decision_table",
    "hit_policy": "priority",
    "inputs":  [{ "name": "运行时长" }, { "name": "故障次数" }, { "name": "故障等级" }],
    "outputs": [{ "name": "服务等级", "type": "enum" }, { "name": "响应时限", "type": "duration" }],
    "rules": [
      { "priority": 1, "when": [">= 8760h", ">= 3",  "\"P1\""], "then": ["\"金牌\"", "\"2h\""],  "note": "长运行 + 高频 + 一级故障" },
      { "priority": 2, "when": ["",        ">= 3",  "\"P1\""], "then": ["\"银牌\"", "\"4h\""] },
      { "priority": 3, "when": ["",        ">= 1",  "\"P2\""], "then": ["\"银牌\"", "\"8h\""] },
      { "priority": 4, "when": ["",        "",      ""],       "then": ["\"标准\"", "\"24h\""] }
    ]
  },
  "effects": "pure",
  "domain_ext": {}
}
```

要点：这个能力**完全没有 `numeric` 扩展包**（无单位、无精度），证明核心元模型不被数值场景污染；`duration` 类型让"8760h""2h"可直接比较。

配套状态迁移（`derive × decision_table`，输出到枚举属性）：

```jsonc
{ "capability_id": "cap_ticket_state", "kind": "derive",
  "signature": { "output": { "type": "enum" } },
  "implementation": { "kind": "decision_table", "hit_policy": "unique",
    "rules": [
      { "when": ["\"新建\""], "then": ["\"待派单\""] },
      { "when": ["\"待派单\""], "then": ["\"处理中\""] }
    ] },
  "effects": "pure" }
```

### 7.3 领域三 · 采购订单审批与回写（供应链域）—— `act × external` + `assert`

**背景**：采购订单本体，需要在超标时路由审批并回写 ERP。这是**触发类交互**——原方案中无处安放，现在落在 `act`。

```jsonc
{
  "capability_id": "cap_po_approval_route",
  "name": "采购订单超标审批路由",
  "business_definition": "订单金额超阈值时按金额区间路由到对应审批人，并触发回写 ERP",
  "version": "1",
  "kind": "act",
  "signature": {
    "inputs": [{ "name": "订单金额", "type": "number", "required": true, "source": "attribute" }],
    "output": { "type": "object" }
  },
  "implementation": {
    "kind": "external",
    "action_id": "act_erp_approval",
    "input_map": {
      "order_no": "expr: this.订单编码",
      "approver": "expr: cap_call(\"cap_approver_pick\", { 金额: this.订单金额 })",
      "amount":   "expr: this.订单金额"
    }
  },
  "effects": "write",
  "deterministic": false,
  "idempotent": true,
  "triggers": [
    { "event": "instance.updated", "scope": { "object_type": "obj_purchase_order" },
      "when": "this.订单金额 > 100000 and this.审批状态 == \"未提交\"",
      "mode": "sync", "on_failure": "block" }
  ]
}
```

配套的审批人选择（`derive × decision_table`）：

```jsonc
{ "capability_id": "cap_approver_pick", "kind": "derive",
  "signature": { "output": { "type": "enum" } },
  "implementation": { "kind": "decision_table", "hit_policy": "first",
    "rules": [
      { "when": [">= 1000000"], "then": ["\"CFO\""] },
      { "when": [">= 100000"],  "then": ["\"财务总监\""] },
      { "when": [""],           "then": ["\"采购经理\""] }
    ] },
  "effects": "pure" }
```

执行契约体现：`effects=write` → 必须走两段式确认；`deterministic=false` → 强制人工确认 + 全量审计；`on_failure=block` → 校验不通过直接阻断入库。

## 8. 从现有 OntologyFunction 迁移的字段映射

### 8.1 OntologyFunction → CapabilityDefinition

| 现有字段（`schemas/ontology.py:69-80`） | 目标字段 | 迁移规则 | 兼容 |
|---|---|---|---|
| `function_id` | `capability_id` | 保留原值；新建的建议用 `cap_` 前缀，旧 `fn_` 前缀继续有效 | ✅ 无损 |
| `name` | `name` | 直接映射 | ✅ |
| — | `business_definition` | **新增必填**；存量可先用 `name` 回填，编辑时强制补全 | ⚠️ 需补录 |
| — | `version` | 存量填 `"1"` | ✅ |
| — | `kind` | 存量一律 `derive`（Function 语义即纯派生） | ✅ 推导 |
| `expression` | `implementation.body` | 直接迁移，并补 `implementation.kind = "expression"`、`language = "opl-expr/v1"` | ✅ 结构升级 |
| `inputs`（string[]） | `signature.inputs[]` | 每项转为 `{name, type: "string", required: true, source: "param"}`；**类型未知，默认 string**，后续按实际修正 | ⚠️ 类型待定 |
| `output_type` | `signature.output.type` | 直接映射（`string` 默认） | ✅ |
| `side_effect`（bool，恒 False） | `effects` | `false → "pure"` | ✅ 推导 |
| — | `deterministic` | 存量填 `true` | ✅ |
| — | `idempotent` | 存量填 `true` | ✅ |
| — | `triggers` | 存量填 `[]`（保留人工触发） | ✅ |
| — | `depends_on` | 存量填 `[]` | ✅ |
| — | `domain_ext` | 存量填 `{}`；数值类能力补 `numeric` 包 | ✅ |
| — | `enabled` | 存量填 `true` | ✅ |

**结论：现有字段全部有归宿，无一项需废弃。** 迁移是"结构升级 + 默认值填充"，可写一次性脚本完成。

### 8.2 本体文件层面的迁移

`ontologies.json` 中每个本体的 `functions[]` → `capabilities[]`：

- **阶段 1（兼容期）**：保留 `functions[]` 原样，新增 `capabilities[]`；读取时合并，重复的以 `capabilities` 为准。
- **阶段 2（迁移期）**：发布编译时把 `functions[]` 逐条转换为 capability 写入 `capabilities[]`，`functions[]` 置空但保留字段。
- **阶段 3（收敛期）**：移除 `functions[]` 读取逻辑，`OntologyFunction` 仅作为历史数据的反序列化兼容类型。

### 8.3 相邻元模型的衔接映射

| 现有模型 | 衔接方式 | 破坏性 |
|---|---|---|
| `OntologyConstraint`（`rule: "unique"`） | `rule` 保留原生名；**新增可选 `capability_id`** 指向 `assert` 类能力，用于表达跨实例勾稽 | ❌ 无（现有 17 条 unique 约束不受影响） |
| `Action`（外部回写） | 成为 `act` 类能力的 `external` 实现；**新增可选 `when`**（条件表达式）与表达式化 `input_map` | ❌ 无（新增字段，默认关闭） |
| `ObjectAttribute` | **新增可选 `derived: { capability_id }`**，把属性绑定到任一 `derive` 能力（不限于公式，决策表也可） | ❌ 无 |
| SHACL 编译 | 派生属性**不生成必填形状**（值是算出来的）；建议加 `sh:derivedFrom` 注解标注来源能力 | ⚠️ 需 translator 增加分支 |
| MCP tools | 新增 `capability_call`（`side_effect` 由 `effects` 推导） | ❌ 无（新增工具） |

## 10. 实施分层与交付顺序

| 层 | 内容 | 依赖 | 建议优先级 |
|---|---|---|---|
| **L0** 值类型与引用解析 | 9 种类型、4 种取值路径、错误码 | 无 | P0 |
| **L1** 能力元模型 | `CapabilityDefinition`、组合约束校验、`domain_ext` 注册 | L0 | P0 |
| **L2** 执行运行时 | 求值、dry_run、幂等、批量、trace、日志、MCP 暴露 | L1 | P0 |
| **L3** Provider | `expression`（含聚合）→ `decision_table` → `external` → `script` | L2 | expr=P0，其余 P1 |
| **L4** 触发与编排 | 事件源、`when`、拓扑序、Action 衔接 | L2 + Action | P1 |
| **L5** 治理 | 版本、影响重算、**人工纠正回流**（借鉴 NV auto-ontology 的 Learn 环节）、权限、审计、可视化编辑器 | L2 | P2 |

**关键顺序**：L0–L2 一次做对（这是抽象，改起来最贵）；L3 的 Provider 可逐个加，每个都不影响内核。

## 12. 决策记录

### 12.1 表达式方言：采用 CEL（附 NVIDIA auto-ontology 调研）

**调研对象**：`NVIDIA/auto-ontology`（Apache-2.0，2026-10-21 GTC Berlin 随 Agent Knowledge Foundation 开源）。

| 维度 | 事实 |
|---|---|
| 定位 | Python 框架，构建 semantic graph-based reasoning layers，主打 deterministic query generation |
| 元模型 | `terms / attributes / foreign keys` → 导出为 Ossie 的 `dataset / field / metric / relationship` |
| **计算表达** | **text-to-SQL**（SQLGlot 多方言）+ Kumo **PQL**（预测路径）。**未见独立的派生指标公式 DSL，也未见 CEL** |
| 依赖 | 强绑定 NVIDIA API catalog / NIM（`nvapi-` key，Kumo 无 SaaS 回退） |
| 数据源 | 证据仅关系型（PostgreSQL / MySQL / Databricks），向量亦落在 Postgres |
| 治理 | 明确声明**不接受外部贡献** |

**对我们的三点判断**

1. **它解决不了公式层的问题。** 它把业务问题编译成 SQL 打到数仓；我们要的是跨本体实例的确定性求值，数据落在 Neo4j / Jena / JSONL，不是关系库。引入它等于引入一套 NIM 依赖 + 关系型假设，**与本项目自托管、非关系存储的现状冲突**。
2. **但有三处值得直接借鉴**：
   - **provenance 粒度**：每次预测产出一条记录，含 `graph / engine 与 prompt 版本 / edges 来源 / model / query / timings / outcome`，**失败也记录**。我们的 §6.2 trace 应补齐 `engine_version / dialect_version / timings`，并同样记录失败。
   - **校验链**：evidence-grounded + intent validation + SQL validation + 重试。对应我们的"导入前 dry_run + assert 前置校验"。
   - **Learn（把认证过的纠正回流进本体）**：对应我们的版本与影响重算，建议补一条 `corrections` 回流机制（人工纠正结果可回写为基线或公式修正建议）。
3. **不采纳**：NIM 强依赖、关系型假设、不接受外部贡献（无法按需定制）。

**CEL 决策：采用，但只作为可替换的一种实现**

采纳理由：Google 开源、语言层面即**无副作用**（天然匹配 `effects=pure`）、静态类型、有成熟 Python 实现（`cel-python`）、沙箱安全、可对子表达式单独求值（便于生成 §6.2 的 trace）。

风险与应对：

| 风险 | 应对 |
|---|---|
| CEL 无多步顺序绑定（成本公式有 C/D/E/F 中间变量） | 外层包 binding 列表，逐步求值，每步写入 trace |
| CEL 无 `lookup`（跨对象维度匹配） | 自定义白名单函数 `lookup()`；**这会形成方言分支，需明确记录** |
| 聚合（`Σ` over list）表达笨拙 | 用 comprehension，或提供 `sum() / map() / filter()` 辅助函数 |
| 单位、精度不在语言内 | 交由 `domain_ext.numeric` + 执行后处理，不污染语言 |
| 被单一库绑死 | 对外只暴露 `language: "opl-expr/v1"`，**CEL 是 v1 的实现而非契约本身** |

**结论**：采用 CEL 作为 expression Provider 的 v1 实现；平台自持方言标识与函数白名单，保留替换实现的余地。

### 12.2 script Provider 延后至 P2

采纳。MVP 仅提供 `expression` / `decision_table` / `external` 三种实现，§3.3(c) 标注为 P2。
注意：**即使 P2 引入 script，`act` 类仍禁用**（见下）。

### 12.3 act 类禁用 script：改用什么实现，有什么弊端

**实现方式：三段组合，副作用只由 Action 产生**

| 环节 | 用什么 | 产出 |
|---|---|---|
| 是否该触发 | `expression` / `assert` 能力 | 布尔 |
| 走哪条路（路由、选审批人、选模板） | `decision_table` | 枚举 / 参数 |
| 入参怎么算 | `expression` | 数值 / 文本 / 对象 |
| **真正的副作用** | `external`（Action：MCP tool / webhook / rest） | 外部写 |

复杂场景用 §3.3(e) 的 `pipeline` 串联多个 `pure` 能力，副作用仍只由 `action_id` 产生——"复杂逻辑"与"副作用"在结构上被强制分离。

**弊端（必须提前知道）**

1. **多步分支与循环无法在单个能力内表达** —— 要拆成多个能力靠 `pipeline` / `depends_on` / `triggers` 串联；真正的多步人工流程应交给独立流程引擎（§10 已排除在范围外）。
2. **可用性受限于 Action 现有实现** —— 重试、超时、幂等、补偿都依赖 Action；而平台当前 Action 回写标注"仅展示·回写未开发"，**act 类能力能否真正落地，取决于 Action 回写何时完成**。这是最大的现实约束。
3. **数据转换能力弱** —— `input_map` 是扁平键值映射，数组重塑、多行 payload、富文本拼接都很别扭，往往要外部系统侧适配。
4. **能力实例膨胀** —— 一个业务动作可能拆成 3–4 个能力（校验 / 路由 / 映射 / 回写），命名与治理成本上升。
5. **可观测性分散** —— 跨能力执行必须统一 `trace_id` 串联，否则排障时看不到完整链路。

**缓解**：P1 提供 `pipeline` 组合与全链路 `trace_id`；`input_map` 在表达式层面支持嵌套与 `list` 构造（不引入脚本）。

### 12.4 存储层级与共享：本体级，发布后才可共享

采纳，且与平台既有生命周期天然一致（本体 `draft → active` 才写入 Jena 并被 MCP / 图谱消费）。

- 能力挂在本体下（`ontology.capabilities`，与 `objects` / `constraints` 同级），语义内聚。
- 能力自身 `status: draft | active`；**本体 publish 时，其下 `active` 的能力才注册到 MCP 与共享库**。
- `visibility: private | project | shared`（默认 `private`），**仅在 `status=active` 时生效**，draft 一律不可被外部引用。
- **跨本体引用必须锁版本**：引用方记录 `capability_id + version`；被引用方升版不自动跟随，需显式升级——避免出现"改了公式，别人昨天的结论也跟着变了"。
- 已发布能力如需修改：改动落在 draft，**再次发布产生新 version，旧版本保留**，保证历史结果可追溯。

### 12.5 决策表编辑：UI + Excel 导入双路径

采纳，两条路径面向不同场景：

| 路径 | 适用 | 关键要求 |
|---|---|---|
| **UI 表格编辑** | 小规模（建议 ≤ 20 条规则）、在线调整、即时反馈 | 实时校验：命中冲突（`hit_policy=unique` 时规则重叠）、覆盖缺口（存在无命中组合且无 `default_output`）、输出类型与 `signature` 是否匹配 |
| **Excel 导入** | 批量维护、业务人员离线编写 | **必须走平台既有归化铁律：preview → 候选（待审核）→ 人工 approve → 校验 → 落库，禁止直落** |

Excel 导入的三个必须：

1. **语法统一**：条件列使用与 UI 相同的表达式语法（**不是 Excel 公式语法**），导入 preview 阶段展示解析结果，解析失败逐行标出。
2. **校验项**：规则重叠、覆盖缺口、输出值是否落在 `enum` 白名单、输入/输出列数与 `signature` 是否一致。
3. **支持 round-trip**：提供"导出为 Excel"，业务人员离线改完再导入，形成闭环。
