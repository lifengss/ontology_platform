# P2 本体录入清单 · 服务产品成本核算（严格按材料版）

> 用途：照此表在「建模」页逐对象录入。共 **17 个对象类型**。
> 原则：**只建材料里真实存在的对象、属性和关系；材料没有的一律不建**（不推断、不补位、不做"将来可能有用"的字段）。
> 依据：`成本基线.xlsx`（15 表）+ `成本核算逻辑.xlsx`（6 表）+ `通用服务器原厂维保_成本核算说明.docx`
> 生成日期：2026-10-27

---

## 0. 录入前必读

### 0.1 四条统一规则

| # | 规则 | 说明 |
|---|---|---|
| 1 | **对象 ID / 属性 ID 一律 ASCII** | 前缀 `obj_` / `attr_`，只用小写字母、数字、下划线。中文只出现在「显示名称」。 |
| 2 | **上级对象（父类）全部留空** | 材料里没有任何 is-a 继承关系，17 个对象全为根对象。 |
| 3 | **stable_key 由后端自动取，UI 无入口** | 建模表单**没有** stable_key 字段（对象卡片只有 对象ID/名称/上级对象/描述/属性/关系）。后端三级回退自动取值：**第一个「必填 + string」属性 → 第一个 string 属性 → 第一个属性**。想让某属性成为主键，只需把它放在**属性列表第一行**、勾**必填**、类型 **string**。本清单每对象的主键属性均已排在第一位，照抄即生效。⚠️ 不要在主键属性前面插入别的必填 string 属性，否则主键漂移。 |
| 4 | **业务定义填进「描述」框** | 表单只有「描述」输入框（对应 `description`），后端按 `business_definition or description` 回填业务语义定义（<5 字才用"XX的业务语义定义"兜底）。下表给的业务定义**直接复制进「描述」框**。 |

### 0.2 唯一一处"材料没有但必须有"的字段

平台要求每个对象有 stable_key（单属性主键），而 `维保服务产品`、各类基线表在材料里都是**复合维度**（区域+服务类型、客户+环节+境内外…），没有单一业务主键。

处理：统一加一个 `编码` 属性（string，必填）作为技术主键，取值为"维度拼接"，例如 `MTP-国内-三年5×10×NBD`、`MGT-阿里-实施-国内`。**这是平台约束，不是材料字段**，其余属性一律只来自源表。

### 0.3 录入顺序与关系时机

```
第1批（无依赖）：客户 → 区域 → 产线 → 机型 → 物料/备件
第2批（基线）：实施人工 → 售后人工 → 管理 → 备件辅助 → 现场服务率
              → 部件故障率 → 人天 → 服务水平系数 → 汇率 → 差旅 → 人员驻场
第3批（主表）：维保服务产品
```

**关系不必等全部录完**：关系的「目标对象 ID」输入框带自动补全，候选来自**当前表单内已填 ID 的全部对象**。只要目标对象的 ID 已填进表单，就能立刻给源对象加关系。

建议节奏：先把 17 个对象的 ID + 名称 + 属性全部录完（属性顺序严格按清单），再回头给「维保服务产品」加 2 条关系。

## 附录 B：宽表转长表规则（录实例时执行）

| 源表 | 原形态 | 目标对象 | 转换 |
|---|---|---|---|
| 实施人工（国内 / 海外BATZ） | 实施类型或机型 × 客户 × 4 个 U 数档列 | 实施人工成本基线 | 4 列拆 4 行 |
| 售后人工（国内 / 海外） | U数 × 客户 × (4 产品类别 × 4 响应级别) | 售后人工成本基线 | **16 列拆 16 行** |
| 管理成本 | 客户 × (实施/售后) × (境内/海外) | 管理成本基线 | 4 列拆 4 行，共 20 行 |
| 人员驻场成本 | 产线 × 等级 × 13 区域列 | 人员驻场成本基线 | 13 列拆 13 行 |
| 备件辅助成本 | 16 列不同度量 | 备件辅助成本基线 | **不拆**，一列一属性 |
| 部件故障率 | 部件类型 × (2 适用产品 × 6 客户细分) | 部件故障率基线 | 6 列拆开 |

**判断口诀**：同一度量被维度切开 → 转长表；多个不同度量并列 → 保持宽表。

## 附录 C：本期只建这 2 条关系

材料里能直接落地的跨对象关系只有两条（其余维度的对应关系主表没有列支撑，不建）：

| 关系 | 名称 | 目标对象 | 基数 | 逆向名 | 材料依据 |
|---|---|---|---|---|---|

**录入时的两个注意点**：

1. 关系表单**没有 `inverse_name`（逆向名）输入框**——表单只采集 `id / name / target_object / cardinality` 四个字段。上表"逆向名"列**录不进去，先忽略**。
2. 基数下拉默认 `many_to_one`，第二条 `rel_product_material` 务必手动改成 `many_to_many`。

**明确不建的关系及原因**：

| 曾考虑的关系 | 不建原因 |
|---|---|
| 机型 → 所属产线 | `机型列表` 表只有机型/对外型号/U数三列，**无产线列**，材料里没有这个事实 |
| 维保服务产品 → 客户 | 主表 114 列中**无客户列**，核算结果是按区域+服务类型聚合的 |
| 维保服务产品 → 机型 | 主表**无机型列**（只有部件PN/配置），机型只出现在独立的机型列表里 |
| 基线表 → 客户 / 产线 | 基线表里客户、产线是**属性列**，不是实体引用；建了会与属性重复，且实例录入需先建大量关联实例 |
| 现场服务率基线 → 客户 | 该列混用客户与产品子类两种语义，做实体引用会语义错乱 |
