# 平台修改建议：计算能力与公式引擎

> 场景驱动：本体「维保服务产品成本模型」已完成建模与 2297 条实例入库，现需在**平台内**完成成本计算（各项成本、合计、占比），而非在平台外用脚本或让大模型直接算。
> 结论先行：**平台目前不具备任何数值计算能力**。元模型预留了一个空壳，引擎、API、UI 全部缺失。
> 本文只给需求与验收标准，不含代码改动。

## 二、为什么不能用现有能力凑

1. **推理 ≠ 计算**。`impact_inference` 能告诉你"改了人工基线，这 33 个产品受影响"，但不会告诉你影响后的成本是多少。它是布尔/集合语义，不是数值语义。
2. **Action ≠ 计算**。Action 是副作用写回，语义上必须 `side_effect=True`，且要人工确认令牌。而成本计算是无副作用的纯函数求值——两者在本体元模型里本来就是被刻意分开的（`OntologyFunction.side_effect` 恒为 False）。
3. **不能让大模型直接算**。这正是本项目要解决的问题：公式散落在 Excel 单元格里，靠 Agent 心算必然幻觉。公式必须是平台里**一等公民、可版本化、可溯源**的资产。

## 二·补 公式不是关系：一个必须先澄清的槽位边界

> 来源：另一轮关于「公式是否可以建成关系」的讨论结论（用户确认后并入本文）。与本文 G1–G14 无冲突，补足了本文未覆盖的一条**禁止项**。

平台的 `ObjectRelation` 定义是 `id / name / target_object（必填）/ cardinality / inverse_name`——**必须有目标对象类型，连的是实例到实例的引用边**，实例化时由数据指定"这一行引用哪一行"。

而公式回答的是"**某个属性的值怎么算出来**"：

```
E（MA人工成本） = MA成本基线 × 现场服务率
```

它没有目标对象，不产出一条边，产出的是一个**数值**。两者本质不同：

| | 关系 | 公式 |
|---|---|---|
| 连什么 | 实例 ↔ 实例 | 属性 ← 其他属性 / 基线值 |
| 实例化时 | 数据指定引用哪一行 | 无需指定，按维度匹配后算出 |
| 产物 | 图中的一条边 | 一个数值 |
| SHACL 表达 | `sh:class` / `sh:node` | **无对应构造**（需 `sh:derivedValue` 或规则引擎） |

本项目材料里的 6 个公式（见第五节）全部是"跨对象取值后算一个数"，不是建一条边。

**由此补一条禁止项**（已并入第七节）：❌ **不得把公式塞进 `ObjectRelation`**。混在一起会让模型既跑不通 SHACL，也说不清语义——这与"不塞进 Action、不塞进 constraints"是同一类边界。

## 三、目标能力定义

计算能力应拆成两层，分别对应 TBox 与 ABox：

| 层 | 名称 | 语义 | 例子 |
|---|---|---|---|
| TBox | **派生属性**（Derived Attribute） | 挂在对象类型上的公式字段，读实例时实时求值 | `维保服务产品.人工成本 = 人工基线单价 × 工时系数` |
| TBox | **本体函数**（OntologyFunction） | 命名的、跨对象的多输入计算 | `计算维保成本(产品编码, 服务年限) → {各项成本, 合计, 占比}` |
| ABox | **求值执行** | 给定实例/参数 → 返回数值 + 溯源链 | 对 33 个产品批量求值，导出成本 list |

三条硬约束（建议写进设计原则）：
- **确定性**：同一输入永远同一输出，禁止随机数、当前时间、LLM 调用参与求值。
- **无副作用**：求值不改实例、不改本体，结果走独立结果集（可显式选择"落库为派生字段"）。
- **可溯源**：每个输出值必须能回溯到「公式 + 输入实例 id + 输入属性 + 输入原值」。

## 四、缺口清单与修改建议

### P0 · 最小可用闭环（有了它就能在平台里算成本）

**G1 · 表达式语言与求值引擎**

> **已决议（2026-10-28，详见《能力层元模型设计》§12.1）**：采用 **CEL 作为 v1 实现底座**，封装在自有方言标识 `opl-expr/v1` 之后（可替换）。下列"语法需求"是对方言**能力**的要求，不再要求自研解析器。

- 现状：无。
- 需求：新增受限表达式语言与安全求值器。
  - **实现底座：CEL**（Google 开源）。采纳理由：语言层面**天然无副作用**（匹配 `effects=pure`）、静态类型、`cel-python` 成熟、沙箱安全、**可对子表达式单独求值**（正好用于生成溯源 trace）。
  - **对外只暴露 `language: "opl-expr/v1"`，CEL 是 v1 的实现而非契约** —— 保留日后换实现的余地，避免被单一库绑死。
  - 语法覆盖面要求不变：四则运算 `+ - * /`、括号、取负；比较与逻辑；条件表达式；内置函数白名单（`round(x,n)`、`min/max`、`abs`、`if_null(x,d)`、`sum(list)`、`coalesce`）。
  - 禁止：`eval/exec`、任意函数调用、字符串插值执行。无论底座是 CEL 还是自研，都必须走**白名单校验**（CEL 侧用声明式函数白名单 + 类型检查，禁止自定义函数逃逸）。
  - 除零、类型不匹配、空值参与运算必须返回结构化错误（含出错的子表达式位置），不能抛裸异常。
- **CEL 的三个已知缺口与应对（必须落实）**：

  | 缺口 | 应对 |
  |---|---|
  | 无多步顺序绑定（成本公式有 C/D/E/F 中间变量） | 外层包 **binding 列表**，逐步求值，每步写入 trace |
  | 无 `lookup`（跨对象维度匹配） | 自定义白名单函数 `lookup()`；**由此形成方言分支，须在方言文档中明确记录** |
  | 聚合（`Σ` over list）表达笨拙 | 用 comprehension，并提供 `sum() / map() / filter()` 辅助函数 |

- **不采纳 NVIDIA `auto-ontology`**（已调研，Apache-2.0，2026-10-21 开源）：其计算表达走 text-to-SQL（SQLGlot）+ Kumo PQL，**无派生指标 DSL**；强依赖 NVIDIA NIM、数据源假设为关系型、明确不接受外部贡献，与本项目自托管 + Neo4j/Jena/JSONL 的现状冲突。但**借鉴其 provenance 粒度**（含 engine 与 prompt 版本、timings，**失败也记录**）、校验链，以及 **Learn 环节**（人工纠正回流进本体）→ 对应补进 G13 日志与 G12 影响重算。
- 验收：`round(208.2404 * 0.218895, 4) == 45.5829`；`1/0` 返回 `DIV_ZERO` 错误并指出子表达式。

**G2 · 取值路径（跨对象引用）** —— 这是成本计算的命门

- 现状：实例是扁平 KV，无跨对象取值手段。主表 33 行要引用 `人工成本基线`、`RMA 基线`、`管理成本基线` 的值，目前只能靠外部脚本 join。
- 需求：表达式支持两种引用形式：
  1. **关系导航**：`this.适用区域.税率`、`this.配置部件[].单价`（关系名直接引用，cardinality 为 many 时得到列表，配合 `sum()` 聚合）。
  2. **按主键定位**：`obj_aftersales_labor_baseline[编码 == "AL-DOM-065"].单价` —— 用对象 id + 属性 id + 值匹配定位到唯一实例，再取其某属性。
  3. **维度匹配**（建议 P0 一并提供，成本场景强依赖）：`lookup(对象id, {U数: this.U数, 客户: this.客户, 服务等级: this.服务等级}, "单价")` —— 按多个维度值组合查找唯一基线实例，命中 0 条或多条时报错（不静默取首条）。
- 验收：`lookup()` 命中多条时必须报 `AMBIGUOUS`，不得以"取第一条"蒙混过关。

**G3 · Function 的持久化与执行 API**

- 现状：`Ontology.functions` 字段能存，但无端点。
- 需求（复用现有元模型，不另起炉灶）：
  - `GET/POST/PUT/DELETE /api/ontologies/{ontology_id}/functions`（项目隔离照旧带 `project_id`）。
  - `POST /api/ontologies/{ontology_id}/functions/{function_id}/execute`，body：`{ "bindings": {...}, "dry_run": true }`，**默认 dry_run**，dry_run 只返回求值结果与溯源，不写任何东西。
  - 批量：`POST .../execute-batch`，对一组 bindings 求值，返回结果集（对应"生成成本 list"）。
  - `OntologyFunction` 建议扩字段：`version`、`unit`（单位）、`precision`（小数位）、`rounding`（`half_up`/`half_even`/`none`）、`description`、`enabled`、`depends_on`（依赖的其他 function，用于顺序与影响分析）。
- **已决议（存储层级与共享）**：能力**挂在本体级**（`ontology.capabilities`，与 `objects` / `constraints` 同级），不设独立的项目级共享库；随本体发布才可被共享。
  - 能力自身带 `status: draft | active` + `visibility: private | project | shared`（默认 `private`）；**本体 publish 时，其下 `active` 的能力才注册到 MCP 与共享库**，draft 一律不可被外部引用——与平台既有 `draft → active` 生命周期完全一致。
  - **跨本体引用必须锁版本**：引用方记录 `capability_id + version`，被引用方升版不自动跟随（避免"改了公式，别人昨天的结论也跟着变"）；已发布能力修改落在 draft，再次发布产生新 version，**旧版本保留**以保证历史结果可追溯。
- 验收：删除被其他 function 依赖的 function 时返回 422 并列出依赖方；draft 能力被 MCP 调用时返回 403。

**G4 · 建模页 Function 区块**

- 现状：无入口。
- 需求：建模页新增「计算函数」区块（建议放在「全局约束」之后），每行包含：
  - 名称、输出类型下拉（复用 `data_type` 6 种枚举）、单位、精度/舍入方式；
  - **输入参数列表**（参数名 + 类型 + 来源说明）；
  - **表达式编辑框**（多行），右侧提供「可引用对象/属性」的下拉插入按钮（插入 `obj_x.attr_y` 字面量，避免手打出错）；
  - **语法校验按钮**（调用 G3 的校验端点，实时报未知属性/类型不匹配/括号不配对）；
  - **试算按钮**：选一个实例 → 就地求值 → 展开显示「取值来源：实例 id / 属性 / 原值」的溯源树。
- 验收：表达式里引用了不存在的属性 id，保存前即被拦截并高亮。

**G5 · 结果溯源与成本清单导出**

- 现状：无。
- 需求：执行结果除数值外，必须带 `sources: [{instance_id, object_type, attribute_id, value}]` 与 `formula_trace`（逐步代入的中间值）。结果集支持导出 Excel（对齐现有导入格式，便于回灌与比对）。
- 验收：导出的清单里，每一行成本都能点出"它由哪个基线实例的哪个值得来、乘了什么系数"。

### P1 · 从"能算"到"好用"

**G6 · 派生属性**（⚠️ 口径已修订，见 §8.6）：`ObjectAttribute` 增加可选 `derived: bool` + `capability_id`（**不再直接挂 `formula` 字符串**）。发布编译时派生属性**不写 SHACL 必填**（值是算出来的），但需在 SHACL 中标记为 `sh:derived` 或等价注解，避免导入时被判为缺失。读实例接口增加 `?include_derived=true`。
> 修订理由：绑 `capability_id` 而非公式字面量，状态字段才能由决策表驱动——**派生属性绑的是"任一 derive 能力"，不是"只能绑算术公式"**。

**G7 · 聚合与分组**（⚠️ 建议**提到 P0**：`F = Σ(单价 × 故障率)` 是材料 6 条公式里唯一的聚合式，缺此项 F 无法表达）：`sum/count/avg/min/max` 支持作用于关系导航得到的列表；结果集支持按维度 `group_by` 汇总（例如按区域汇总成本）。

**G8 · 单位与量纲**（⚠️ 已下沉，见 §8.6）：**不进核心元模型**，作为 `domain_ext.numeric` 扩展包（`unit` / `precision` / `rounding` / `currency`）。求值引擎对二元运算做单位一致性检查（元 × 系数 合法；元 + 次 报 `UNIT_MISMATCH`）；币种预留 `currency` 字段与汇率表。
> 下沉理由：单位/精度是数值场景专属，文本、状态、日期类能力挂 `unit` 会很别扭——放进扩展包后各场景互不污染。

**G9 · 批量试算（What-if）**：`POST .../simulate`，body 支持"临时覆盖某些基线值"，计算在新假设下的成本，不改任何实例。用于回答"人工基线涨 10% 会怎样"。

**G10 · MCP 暴露计算工具**：新增 `function_call`（`side_effect: false`），入参 `{ontology_id, function_id, bindings}`。这样 Agent 问"这个产品成本多少"时，是**调用平台公式**而不是自己心算——这是本项目作为语义底座的价值兑现点，优先级其实很高，若希望尽快验证 Agent 消费路径，可提到 P0。

### P2 · 治理与工程化

- **G11 · 计算型约束**：`OntologyConstraint.rule` 扩展支持校验型表达式（如 `合计 == 人工 + 备件 + 管理 + 税金`），导入/重算后自动勾稽。
- **G12 · 影响重算**：基线实例变更 → 反查依赖它的 function 与已算结果 → 标记 `stale` 并给出重算清单（可与现有 `impact_inference` 的 R1 复用）。
- **G13 · 计算日志**：复用日志页，记录 `function_id / 输入 / 输出 / 执行人 / 版本 / 耗时`，便于审计"这个数是谁按哪版公式算的"。
- **G14 · 决策表与可视化编辑**（已决议：**UI + Excel 导入双路径**）：
  - **决策表**作为一种独立实现（`implementation.kind = decision_table`），与表达式并列，用于"多条件分档"类逻辑（服务等级判定、审批路由、分档系数）。
  - **路径一 · UI 表格编辑**：适用小规模（建议 ≤ 20 条规则）、在线调整。必须实时校验：命中冲突（`hit_policy=unique` 时规则重叠）、覆盖缺口（存在无命中组合且无 `default_output`）、输出类型与 `signature` 是否匹配。
  - **路径二 · Excel 导入**：适用批量维护、业务人员离线编写。**必须走平台既有归化铁律：preview → 候选（待审核）→ 人工 approve → 校验 → 落库，禁止直落**。三个必须：① 条件列使用与 UI 相同的表达式语法（**不是 Excel 公式语法**），preview 阶段展示解析结果、解析失败逐行标出；② 校验规则重叠、覆盖缺口、输出值是否落在 `enum` 白名单、列数与 `signature` 是否一致；③ 支持**导出为 Excel 做 round-trip**，形成闭环。
  - **积木式公式编辑器**（原 G14 的 DSL 可视化）建议在表达式方言稳定后再做，优先级最低。
- **G15 · `script` Provider（沙箱）**：**延后至 P2**（采纳用户建议）。MVP 只提供 `expression` / `decision_table` / `external` 三种实现。注意：**即使 P2 引入 script，`act` 类仍禁用**（见 §9 决策 3）。

## 五、落到本项目的具体形态（供开发对齐口径）

### 5.1 材料中的公式全集（权威口径，来自主表列头 + 成本核算说明）

主表「通用服务器原厂维保」的 r1/r2 双层表头给出了成本项，**共 6 条公式**：

| 列 | 成本项（r1/r2） | 公式 | 实测校验（r3 国内 · 三年5×10×NBD） |
|---|---|---|---|
| C | MA成本基线 | *（输入，来自基线实例）* | 208.2404 |
| D | 现场服务率 | *（输入）* | 0.2188954 |
| **E** | **MA人工成本** | `E = C × D` | 208.2404 × 0.2188954 = **45.5829** ✓ |
| **F** | **备件直接成本** | `F = Σ(单价 × 故障率)` ← **含聚合** | 17.0816 |
| G | 辅助成本基线 | *（输入）* | 88.7443 |
| H | 现场服务率 | *（输入）* | 0.2188954 |
| **K** | **备件辅助成本** | `K = G × H` | 88.7443 × 0.2188954 = **19.4257** ✓ |
| L | 管理成本基线 | *（输入）* | 583.5679 |
| M | 现场服务率 | *（输入）* | 0.2188954 |
| **N** | **管理成本** | `N = L × M` | 583.5679 × 0.2188954 = **127.7403** ✓ |
| **O** | **成本合计** | `O = E + F + K + N` | 45.5829+17.0816+19.4257+127.7403 = **209.8305** ✓ |
| R | 整机成本 | *（输入）* | 37672 |
| **S** | **维保占比** | `S = O / R` | 209.8305 / 37672 = **0.0055699** ✓ |

欧洲（德国）口径另有两个常数：现场服务率 `D4 = D3 + D3/3×1.2`（三年系数 ×1.4）、综合税率 `J = 0.19`。
E/K/N 三条同构（基线 × 现场服务率），O 是求和，S 是比率，**F 是唯一含聚合的公式**。

> 校验说明：E / K / N / O / S 五条已用 r3 行数值逐条代入复算，与主表原值吻合（✓）。F 依赖 BOM 明细聚合，其明细构成尚需与主表右侧 BOM 区（`AA~AK` 故障率与备件成本、`AS~DD` 良品/不良品损耗等列）逐项复算确认，目前只登记主表原值。

> **因此 G7（聚合与分组）不是可选项**：`F = Σ(单价 × 故障率)` 依赖对 BOM 明细行遍历求和，缺了它 F 无法在平台内表达。建议**从 P1 提到 P0**。

### 5.2 平台内定义的形态（写法示意，以最终 DSL 为准）

```
function_id : fn_maintenance_cost
name        : 维保服务产品成本核算
inputs      : product_code(编码), region(区域)
output_type : float
unit        : 元
precision   : 4 / rounding: half_up

-- 现场服务率（国内 / 海外分档，材料给出三年系数 1.4）
service_rate = region == "国内" ? lookup(...) : lookup(...) * 1.4

-- 各项成本：基线值全部经 lookup 从本体实例取，不硬编码
E = lookup(obj_labor_baseline,  {维度}, "MA成本基线") * service_rate
K = lookup(obj_material,        {维度}, "辅助成本基线") * service_rate
N = lookup(obj_manage_baseline, {维度}, "管理成本基线") * service_rate
F = sum(this.配置部件.map(p => p.单价 * p.故障率))      -- 聚合，依赖 G7
O = E + F + K + N
S = O / this.整机成本
```

关键约束（务必保留）：
- 所有基线数值**只能来自 `lookup()`，不允许写死常量**。硬编码数字是本次建模"只按材料已有内容"原则的天敌。
- 分档系数 `1.4` 这类材料里明确给出的常数，允许出现在表达式中，但建议同时提供"系数基线对象"的改造选项供后续评估。
- `lookup` 未命中必须报错，不允许补默认值——这正是之前 RMA 系数被误当成"平台补默认值"的教训。

## 五·补 两条落地路线（含"公式对象化"方案）

> 来源：另一轮讨论给出两条路，并建议"先跑通实例导入把 P8 闭环，再单独评估要不要加这一层"。
> **该前置条件现已满足**：2297 条实例全部入库、实例列表截断 bug 已修复并验证，17 个对象均有数据。因此现在正是评估路线 B 的时点。

### 路线 A · 平台原生计算能力（本文 G1–G5 + G10）

把 Function 做成平台一等公民：新增引擎 + API + UI，公式在平台内求值。

- 优点：确定性、可溯源、可校验单位、Agent 直接调用不自己算——**终局形态**。
- 代价：需要后端开发（引擎、端点、UI），周期最长。

### 路线 B · 把公式对象化（新增第 18 个对象「成本构成项」）

不动平台一行代码，用**现有建模能力**把公式变成数据：新增对象类型，公式为属性值，用关系把产品与成本项连起来。此时「公式表达式」是**属性**，它参与的链接才是**关系**——公式本身依然不是关系。

建议建模（属性名待定，材料来源已标注）：

| 项 | 内容 | 材料依据 |
|---|---|---|
| 对象 | `obj_cost_item` 成本构成项 | 主表 r1/r2 表头即成本项清单 |
| stable_key | `成本项编码`（列标识 C / E / F / K / N / O / S …） | 材料已有 |
| 属性 | 成本项名称（MA人工成本 / 备件直接成本 / 成本合计 …） | r1/r2 表头，材料已有 |
| 属性 | 公式表达式（`E = C × D`、`O = E + F + K + N` …） | 成本核算说明 + 列关系，材料已有 |
| 属性 | 计算口径说明 | 成本核算说明文字，材料已有 |
| 属性 | 是否聚合项（F 为是） | 由公式形态判定，加工 |
| 属性 | 单位（元 / 比率） | 材料已有 |
| 属性 | 引用基线对象（指向 17 个既有对象之一） | **加工**（非材料原文，需你确认） |
| 关系 | `维保服务产品 —包含成本项→ 成本构成项`（one_to_many） | 主表列与产品的归属关系，材料隐含 |

- 优点：**本周就能做**，无需等平台改造；公式变成可被 MCP 消费的知识，Agent 至少能拿到准确口径，不至于自己编算法。
- **局限（必须讲清楚）**：公式仍以**字符串**存放，Agent 读到后要**自行解析并求值**——没有确定性保证、没有溯源、没有单位与除零检查。路线 B 解决的是"**口径可见**"，不解决"**结果可靠**"。它是通向 A 的过渡增强，不是 A 的替代。

### 对比

| | 路线 A（原生引擎） | 路线 B（公式对象化） |
|---|---|---|
| 是否改平台代码 | 是（引擎 + API + UI） | **否**，纯建模 |
| 计算在哪发生 | 平台求值，Agent 只取值 | Agent 读公式后自己算 |
| 确定性 / 可溯源 | ✅ 强 | ❌ 无保证 |
| 公式对 Agent 可见 | ✅ | ✅ |
| 单位 / 除零 / 精度校验 | ✅ | ❌ |
| 落地周期 | 长 | 短（本次会话即可完成） |
| 与"只建材料已有"原则 | 平台能力，不冲突 | 需新增对象 + 1 条关系 + 2 个加工属性，**属范围扩展** |

### 建议

**B 先行、A 为终局。** 先用路线 B 让公式进入本体、被 MCP 消费，验证 Agent 能否正确理解口径；同时按 P0 推进 A。等 A 落地后，把 B 里的公式表达式迁到 Function 的 `expression` 字段，B 的对象退化为"成本项字典"（保留编码、名称、单位），二者不冲突。

## 七、明确不建议做的事

- ❌ 不让大模型在对话里直接算成本再回写平台（与项目定位冲突，且无法溯源）。
- ❌ 不把计算公式塞进 `Action`（Action 恒 `side_effect=True`，语义错位）。
- ❌ **不把公式建成 `ObjectRelation`**（关系必须有 `target_object`、产物是实例间的边；公式产物是数值，SHACL 无对应构造）。混用会让模型既跑不通 SHACL 也说不清语义。
- ❌ 不在 `ObjectAttribute.constraints` 里扩展计算语义（constraints 是校验，不是生产）。
- ❌ 不用 `eval()` 实现求值器（注入风险 + 无法做溯源与单位检查）。

## 八、通用性评估：从"公式引擎"到"能力层抽象"

> 问题：上述 G1–G14 是围绕成本数值计算设计的。换一个本体（状态机流转、合规判定、触发外部系统）还成立吗？会不会做成一个"只能算成本公式"的硬编码引擎？

### 8.1 先说实话：原方案存在过拟合，有 6 处

| # | 过拟合点 | 为什么只适配成本场景 |
|---|---|---|
| 1 | DSL 只定义算术与聚合 | 字符串拼接、集合运算、日期推算、状态迁移无法表达 |
| 2 | `unit / precision / rounding` 进核心元模型 | 文本/布尔类能力带"单位"很别扭 |
| 3 | `OntologyFunction.side_effect` 恒 False | 把触发类、交互类能力直接排除在外 |
| 4 | `lookup` 只返回标量 | 取集合、取对象引用、取子树都无法表达 |
| 5 | 没有事件源与条件触发 | 只有"人/API 主动调"，没有"实例变更时自动跑" |
| 6 | Function 与 Action 完全断开 | Action 无表达式能力、Function 无副作用能力 → **触发类交互无处安放** |

另有旁证：平台现有扩展点都是**单一枚举、无抽象层**——本体级约束 `rule` 编译器只认 `"unique"`（`modeling_translator:175`），推理规则是 OWL2-RL 的固定集合。**若不先建抽象，新建的能力必然是第二个硬编码特例。**

### 8.2 结论：抽象可复用，但必须把核心与场景专属分离

可复用的内核（与场景无关）：表达式 AST 与求值、引用解析、溯源链、批量执行、dry_run、版本与影响分析。
应外置的部分：语法糖、单位量纲、数值精度、具体函数库。

因此建议把"公式引擎"升级为 **能力层（Capability Layer）**，采用你要的"先抽象、后实例化"结构：

### 8.3 建议的抽象：能力元模型 × 实现 Provider

**元模型（核心，场景无关）**

```
OntologyCapability:
  capability_id, name, version
  kind        : derive | assert | act        # 产出什么语义
  signature   : { inputs: [{name, type}], output: {type} }
  implementation: { kind: expression | decision_table | script | external, body }
  #                                                     ^^^^^^ P2 才提供
  status       : draft | active                # 本体发布后 active 才可被执行与共享
  visibility   : private | project | shared    # 仅 status=active 时生效
  effects     : pure | read | write          # 取代原来的 side_effect 布尔
  deterministic: bool                        # false 时必须 human_required
  idempotent  : bool
  triggers    : [{ event, when }]            # 事件源 + 触发条件
  depends_on  : [capability_id]
  domain_ext  : { ... }                      # 场景专属字段放这里（如 unit/precision/currency）
```

**三个关键设计**

1. **`kind` 决定语义，`implementation` 决定怎么算** —— 二者正交，构成 3 × 4 的能力矩阵（见下图）。成本公式只是其中 `derive × expression` 一格。
2. **`domain_ext` 承接场景专属字段** —— 原 G8（单位/精度）从核心下沉到这里。数值模型挂 `unit/precision`，文本模型不挂，互不污染。
3. **`effects` 用三态取代布尔** —— `pure` 可缓存可重放；`read` 需记录外部读取；`write` 必须 `human_required` + 幂等键。这样触发类交互（原先无处安放）自然落在 `act` 类，并可复用现有 `Action` 作为 `external` 实现。

**值类型要通用**：表达式引擎不应只认数字，建议对齐本体 `data_type` 并扩展为
`number / string / boolean / date / duration / enum / ref(实例引用) / list / object`。
成本计算只是 `number` 上的特例。

**Provider 注册表**：`ExpressionProvider` / `DecisionTableProvider` / `ScriptProvider`（沙箱，**P2**） / `ExternalProvider`（MCP tool、webhook，复用 Action）。**MVP 先交付前两种 + External**；新增能力形态 = 注册一个 Provider，不改核心。

### 8.4 矩阵：3 种 kind × 4 种实现

| | expression | decision_table | script（沙箱，**P2**） | external（MCP/webhook） |
|---|---|---|---|---|
| **derive** 产出值 | **成本 `E = C×D`** ← 本项目 | 服务等级 / SLA 判定 | 复杂排产算法 | 调外部定价服务取价 |
| **assert** 产出布尔+证据 | 勾稽 `O == E+F+K+N` | 合规检查表 | — | 调外部征信校验 |
| **act** 触发交互 | — | 审批路由（谁批） | — | 变更通知 / 回写 ERP |

> 空白格不是遗漏，是**刻意不提供**——比如 `act × expression` 用表达式直接产生副作用，既不可审计也不好理解；`act × script` 见 §9 决策 3。

### 8.5 触发与编排（补原方案缺口）

- **事件源**：实例创建 / 实例更新 / 导入审批通过 / 定时 / MCP 调用 / 人工触发。
- **条件**：`when` 复用同一套表达式（`assert` 类能力天然可当条件用）。
- **执行契约**：`act` 类走现有 Action 的两段式（execute → confirmation_token → confirm），天然满足"重要操作前确认"。
- **顺序与事务**：按 `depends_on` 拓扑排序；单条失败时的回滚策略需明确（建议：同 `effects` 分组，pure 可重试，write 需人工介入）。

### 8.6 与原 G 清单的映射（不推翻，只是重排为分层）

| 层 | 内容 | 对应原条目 |
|---|---|---|
| L0 值类型与引用解析 | 通用类型、关系导航、主键/维度 lookup、集合 | G2、G7 |
| L1 能力元模型 | `kind × implementation` 抽象、domain_ext | G3、G6、G8（下沉）、G11 |
| L2 执行运行时 | 求值、dry_run、幂等、批量、溯源、日志、MCP 暴露 | G1、G5、G9、G10、G13 |
| L3 Provider 实现 | expression（CEL 底座）/ decision_table / ~~script~~（P2）/ external | G1 的 DSL、G7 聚合 |
| L4 触发与编排 | 事件源、when、顺序、Action 衔接 | **新增**（原方案缺失） |
| L5 治理 | 版本、影响重算、权限、审计 | G12、G4 的 UI |

**需修订的两条**：G8（单位/精度）**下沉到 `domain_ext`，不进核心**；G6（派生属性）改为"属性可绑定任一 `derive` 能力"，而非只能绑公式——这样状态字段也能由决策表驱动。

### 8.7 边界：哪些不该塞进能力层

- ❌ **长事务 / 工作流编排**（多步人工审批、跨天流程）——应独立为流程引擎，能力层只提供单步。
- ❌ **外部连接器治理**（凭据、限流、重试策略）——属集成层，能力层只调用不管理。
- ⚠️ **非确定性求值**（LLM 参与判断）——如确需，作为受控 Provider：`deterministic=false` 时强制 `human_required`，且输入输出与提示词全量入审计日志。**默认不提供。**

### 8.8 向后兼容的迁移路径

- 现有 `OntologyFunction` 视为 `kind=derive, implementation=expression, effects=pure` 的**特例**，字段可平滑映射（`expression → implementation.body`、`inputs → signature.inputs`），无需废弃。
- 现有 `OntologyConstraint.rule` 从唯一 `"unique"` 扩展为：`rule` 保留原生规则名，另加可选 `capability_id` 指向 `assert` 类能力——这样"跨实例勾稽"这类 SHACL 表达不了的校验有了去处，且不破坏现有 17 条 unique 约束。
- 现有 `Action` 增加可选 `when`（条件表达式）与表达式化的 `input_map`，成为 `act` 类能力的 `external` 实现。

> 一句话总结：**先建 L0–L2 的通用内核与元模型，成本公式只是 L3 的一个 Provider 实例。** 这样下一个本体（无论数值、状态还是触发）只需注册新 Provider 或新实例，不改核心。

### 9.1 决策 1 补充：为什么不采纳 NVIDIA auto-ontology

`NVIDIA/auto-ontology`（Apache-2.0，2026-10-21 GTC Berlin 开源）定位与本项目高度同构，但**解决不了公式层问题**：其计算表达走 text-to-SQL（SQLGlot）+ Kumo PQL，**无派生指标 DSL，也无 CEL**；强依赖 NVIDIA NIM（`nvapi-` key）、数据源证据仅关系型、**明确不接受外部贡献**。我们要的是跨本体实例求值，数据落在 Neo4j / Jena / JSONL——引入它等于同时引入三处冲突。

**但借鉴三处**：provenance 粒度（含 engine 与 prompt 版本、timings，**失败也记录**）→ 补进 G13；校验链 → 补进导入前 dry_run + assert 前置校验；**Learn（人工纠正回流进本体）** → 补进 G12。

### 9.2 决策 3 展开：act 禁 script 后怎么实现，弊端是什么

**实现方式：三段组合，副作用只由 Action 产生**

| 环节 | 用什么 | 产出 |
|---|---|---|
| 是否该触发 | `expression` / `assert` 能力 | 布尔 |
| 走哪条路（路由、选审批人、选模板） | `decision_table` | 枚举 / 参数 |
| 入参怎么算 | `expression` | 数值 / 文本 / 对象 |
| **真正的副作用** | `external`（Action：MCP tool / webhook / rest） | 外部写 |

复杂场景用 `pipeline` 串联多个 `pure` 能力（共享上下文与 `trace_id`，`assert` 步骤可 `on_false: abort`），副作用仍只由 `action_id` 产生——"复杂逻辑"与"副作用"在结构上被强制分离。

**弊端（五条，第二条最致命）**

1. **多步分支与循环无法在单个能力内表达** —— 需拆成多个能力靠 `pipeline` / `depends_on` / `triggers` 串联；真正的多步人工流程应交给独立流程引擎（§8.7 已排除在范围外）。
2. **可用性受限于 Action 现有实现** —— 重试、超时、幂等、补偿全依赖 Action；而平台当前 Action 回写标注"**仅展示·回写未开发**"。**act 类能力能否真正落地，取决于 Action 回写何时完成**，这是最大的现实约束，建议列入开发前置依赖。
3. **数据转换能力弱** —— `input_map` 是扁平键值映射，数组重塑、多行 payload、富文本拼接都很别扭，往往要外部系统侧适配。
4. **能力实例膨胀** —— 一个业务动作可能拆成 3–4 个能力（校验 / 路由 / 映射 / 回写），命名与治理成本上升。
5. **可观测性分散** —— 跨能力执行必须统一 `trace_id` 串联，否则排障时看不到完整链路。

**缓解**：P1 提供 `pipeline` 组合与全链路 `trace_id`；`input_map` 在表达式层面支持嵌套与 `list` 构造（不引入脚本）。

### 9.3 决策 4 补充：两条必要约束

- **跨本体引用必须锁版本**：引用方记录 `capability_id + version`，被引用方升版不自动跟随——避免出现"改了公式，别人昨天的结论也跟着变了"。
- **旧版本保留**：已发布能力的修改落在 draft，再次发布产生新 version，旧版本保留供历史结果追溯。
