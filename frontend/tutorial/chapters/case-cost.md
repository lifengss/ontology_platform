# 典型案例：维保服务产品成本建模

> **学习目标**：跟一个**完整真实案例**把全流程走一遍——17 个对象的本体建模（含代理主键/N:N 关系/约束）→ 校验发布 → 3 个文件 2277 条实例导入（宽表转长表）→ 批量审核入库 → 图谱/自然语言查询验证 → MCP 发布 → WorkBuddy 接入。本案例是平台"语义底座"定位的完整落地示范。

## 0. 背景与材料

某业务要把「维保服务产品成本核算」搬到平台：产品成本 = 物料成本 + 实施人工 + 售后人工 + 现场服务率等若干基线，按区域/客户/机型维度核算。

| 材料 | 作用 | 本例来源 |
|---|---|---|
| **本体清单**（xlsx/csv） | 对象、属性、约束、主键、关系指向 | 业务域梳理：17 对象清单 |
| **业务数据文件** | 最终导入的实例 | `成本基线.xlsx`（15 表）+ `成本核算逻辑.xlsx`（主表） |

> 好的清单应注明：对象 ID、属性 ID、数据类型、是否必填、约束（长度/正则/枚举/范围）、主键（stable_key）、关系指向与基数。

## 1. 建项目

「设置 → 项目」新建项目（如「成本核算模型」），后续所有操作在此项目上下文。

## 2. 按清单建本体（17 对象）

![表单建模](assets/modeling-form.png)
*建模页：左侧本体列表，右侧对象/属性编辑区*

- **对象**：17 个对象卡片（机型/物料/备件/各成本基线/区域/客户/维保产品…），每个填 id（`obj_` 前缀）、名称、**业务定义**（≥5 字，表单里直接写进「描述」框）；
- **属性**：按清单逐对象录入，**属性顺序严格按清单**（主键要排第一行）；
- **主键（stable_key）**：无输入框，自动判定（第 3 章三级回退）。材料里维度是复合的（如 区域+服务类型）没有单一业务主键的对象，**额外加一个「编码」属性（string、必填、第一行）作代理主键**，取值为维度拼接（如 `IL-DOM-001`）——这是平台约束，不是材料字段；
- **关系**：材料里能直接落地的才建，本例 2 条：

| 关系 | 目标对象 | 基数 | 注意 |
|---|---|---|---|
| 适用区域 | 区域 | N:1 | 主表「区域」列 |
| 配置部件 | 物料/备件 | **N:N** | 下拉默认 N:1，**手动改成 N:N** |

> 没有事实依据的关系**不建**（如 机型→产线：机型列表里没有产线列就不建）。

## 3. 设置约束

![约束编辑器](assets/constraint-editor.png)
*约束编辑器：属性级（长度/正则/范围/枚举）与本体级（unique）*

- **属性级**：物料编码长度 4~64；属性编码正则 `^[A-Za-z0-9\-]+$`；汇率最小值 `0.000001`；服务类型枚举整段粘贴进「枚举」框；
- **保上界忠于真值**：现场服务率有 1.26、巴西税率 1.02 等 >1 的真值 → 删掉 `maximum 1` 只留 `minimum 0`，否则合法数据会被 SHACL 拦；
- **本体级**：如「物料编码唯一」（`rule: unique`，scope 指向物料对象 + 编码属性）。

## 4. 校验并发布

- 保存前过**创建前校验门**（id 唯一、父级无环、枚举合法、业务定义 ≥5 字、主键指向已存在属性…），不通过逐条列出 violations；
- 全过 → `草稿 → 已发布（active）`，翻译器写入 Jena 推理引擎，图谱/MCP 才能消费。

![发布后的本体](assets/ontology-published.png)
*本体状态「已发布」*

> ⚠️ **导入前常需回改本体**：本例导入素材时改了 5 处（否则 1425 条会被拦）——物料对象加主键属性（PN 在两厂重号，不能单独做主键）；两条基线加「区域」属性；售后基线客户改非必填 + 枚举追加 `STR`；两处删掉 `maximum 1`。流程：**改本体 → 保存 → 校验 → 重新发布 → 再导数**。

## 5. 导入实例（3 文件 / 2277 条）

![实例导入页](assets/ingest-page.png)
*多对象批量导入：一个 sheet 对应一个对象，sheet 名即对象 id*

- 用**多对象批量导入**：一个 sheet 对应一个对象，sheet 名即对象 `id`，逐个上传：

| 文件 | 对象数 | 条数 |
|---|---|---|
| 成本基线 batch1 | 11 个对象 | 872 |
| 售后人工成本基线 batch2 | 1 个对象 | 1372 |
| 维保服务产品主表 batch3 | 1 个对象 | 33 |
| **合计** | | **2277** |

- **先小后大**：先导 batch3（33 条）验证映射，再 batch1/batch2；
- **宽表转长表口诀**：同一度量被不同维度切开 → 拆多行（如 主表「成本 = 物料列 + 实施人工列 + 售后人工列」→ 每列一行，度量名进属性）；多个**不同含义**的度量并列（仓储/配送/物流/税率）→ 各留一个属性，不拆行；
- **口径映射**：材料枚举与本体枚举不一致时按本体归一（如 `3U/4U/5U` → 本体枚举 `2U高密度及3U4U5U`）；
- **空值跳过**：源表「——」空值行/列导入时跳过；
- 每批「预览」双校验通过 →「生成候选」。

## 6. 审核入库

![候选审核](assets/candidates-review.png)
*候选审核区：批量批准入库*

- 候选区按属性渲染成表格，人工抽查关键行（主键、枚举值、关系主键）；
- **批量批准入库**（如 batch2 的 1372 条整组过）→ SHACL 校验 → 入库；
- 违例行单条编辑后重批。

## 7. 视图验证

- 实例列表：33+872+1372 条按对象可查；
- 图谱三视图：知识图谱点选产品看「配置部件」N:N 血缘；
- **自然语言查询**（需 LLM）：「有多少种机型？按 U 数分组」→

```
机型 53 种：1U=14 / 2U=32 / 4U=7
```

与平台内列表统计一致，即数据链路闭环。

## 8. MCP 发布

- MCP 页选中本体**发布** →「生成 token」（旧 token 立即失效）；
- 端点：`/mcp/{项目id}`（streamableHttp，`Authorization: Bearer <token>`）；
- 4 工具：`ontology_query` / `instance_get` / `inference_trace` / `action_invoke`；
- `ontology_id` 传 **32 位 hex ID**（如 `1f2ea950c2914a69a994da880e676531`），传名称可能报 `NOT_PUBLISHED`。

## 9. WorkBuddy 接入（防假连通）

- WorkBuddy 把 HTTP MCP 一律当 OAuth 型 → 用**本地 stdio bridge**：`~/.workbuddy/mcp.json` 配 `backend/mcp_stdio_bridge_v2.py --project <项目id>`（完整 JSON 见第 16 章）；
- **不要写 `env`**（Windows 丢 `SystemRoot` → `WinError 10106`）；
- **验证**：问训练数据不可能知道的问题（本例 §7 的机型分组题），返回真实数据 = 真连通；
- token 轮换/配置变更后必须**完全重启 WorkBuddy**（停用→启用不够）。
