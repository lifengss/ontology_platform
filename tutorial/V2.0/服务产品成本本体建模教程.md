## 第 0 步｜登录与鉴权

**✅ 目标**：以管理员登录，获得 `Bearer token`，之后所有 `/api/*` 请求带 `Authorization: Bearer <token>`。

**🖥️ 平台侧操作/界面（截图说明）**
- **设置页 → 登录**：输入管理员账号密码登录。初始管理员 `admin`。
- 界面出现「当前用户 + 权限矩阵（角色/租户/资源授权）」概况。
- 说明：初始密码来源二选一——① 环境变量 `ONTOLOGY_BOOTSTRAP_ADMIN_PASSWORD`；② 旧版 `backend/secrets/bootstrap_admin.txt`（**新版已废弃明文密码文件**，改为环境变量；但库内密码哈希在重启后仍有效，旧密码仍可登录）。

**API（脚本侧）**
```
POST /api/auth/login?mode=bearer
→ data.token
```

> ⚠ 踩坑：`localhost` 在 Windows 会解析到 IPv6 `::1` 导致请求挂起，一律用 **`http://127.0.0.1:8000`**。

## 第 3 步｜本体建模（对象/属性/关系/稳定键）

**✅ 目标**：按 docx 取数关系，构建完整本体（主数据对象 + 结果对象）。

**🖥️ 平台侧操作/界面（截图说明）**
- **建模页 → 新建本体**：名称、版本、建模类型（manual）。
- **对象画布**：每类对象一张卡片，卡片内列出属性（名称/类型/必填/约束）与关系（目标对象/基数/反向名）。
- **对象详情**：每个对象必填「**业务语义定义**」（≥5 字）与「**稳定键 stable_key**」（指向本对象某 string 属性，用于唯一识别；组合情况用合成 `code` 字段）。
- 提交后本体处于 `draft`。

**本次构建的对象（10 + 后续 9 = 19 个）**

| 对象 id | 名称 | 稳定键 | 关键属性 | 用途 |
|---|---|---|---|---|
| `model` | 服务产品机型 | model_code | model_code/u_count/remark | 机型→U数档→人工基线 |
| `labor_baseline` | 售后人工成本基线 | code | u_group/customer/product_line/region/service_class/unit_cost | E=C×D |
| `onsite_rate_baseline` | 现场服务率基线 | code | product_line/customer/region/rate | 现场服务率 D |
| `spare_aux_baseline` | 备件辅助成本基线 | code | country/unit_nd/unit_4h/unit_rma/unit_arma/tax_rate | K=H×G |
| `mgmt_cost_baseline` | 管理成本基线 | code | customer/phase(实施/售后)/region/value | N=L×M |
| `service_level_coeff` | 服务水平系数基线 | code | response_class/coeff | 4H×1.15 等 |
| `failure_rate_baseline` | 部件故障率基线 | code | part_type/product_line/customer/rate | F=BOM×故障率 |
| `part_price` | 备件单价 | part_pn | factory/part_pn/part_desc/unit_price | 备件成本 |
| `bom` | 整机BOM | code | model_code/part_pn/qty/unit_price/cost | F 归集输入 |
| `warranty_cost` | 维保成本核算结果 | code | region/service_type/E/K/N/O/S/P/Q/R | 结果/验证基准 |

> 版本演进（对象随需求补充，均可通过兼容变更提案自动升版本）：v1.0（10 对象）→ v1.1（+人天/差旅/驻场/资金占用基线 + 5 个核算结果对象，19 对象）→ v1.2/v1.3/v1.4（补字段 + 现场人工基线）。

**🖥️ 已发布本体如何再改对象（截图说明）**
- **变更提案（changeset）**：active 本体不可直接编辑。在**建模页 → 该本体 → 变更提案**里补充「model（完整新模型）」，兼容变更会自动升小版本并直接发布（如新增对象/属性）。
- 界面上会生成「版本 diff」：新增了哪些对象/属性，兼容(true)/破坏(false)。

**API**
```
POST /api/ontologies?project_id=...      # 新建 draft
POST /api/ontologies/{oid}/changesets    # 已发布本体的变更提案（model 为完整新模型，兼容→自动升版）
```

> ⚠ 属性约束 `pattern` 只认 ASCII；产品线分组 enum 是**全角括号**（如 `服务器（SV、AI、边缘）`）；枚举值须与源表完全一致才能命中。

## 第 4 步｜导入基线实例（preview → approve）

**✅ 目标**：把《成本基线.xlsx》主数据表导入为实例。走**归化铁律**：`preview → 候选(待审核) → 人工 approve(SHACL) → 落库`。

**🖥️ 平台侧操作/界面（截图说明）**
- **实例导入页 → 选择对象 → 上传 CSV/Excel 或字段映射**：
  - 推荐 `field_map`：`source.records` 为 JSON dict 列表，**空字段直接省略**（避免空串触发 SHACL 枚举/必填报 `Value Literal("") not in list`）。
  - `object_type` 放 **body**；`field_map` 放 **body 且必须非空**（identity map `{k:k}` 也行）。
- **候选队列（待审核）**：每批生成一个 candidate，界面展示逐条实例、健康度。
- **审批**：逐批 `approve`，界面显示 `imported/inserted/dedup/violations`。

**本次导入清单（全部 0 违规）**

| 对象 | 条数 | 说明 |
|---|---|---|
| model | 53 | 机型列表 |
| labor_baseline | 60 | 国内通用服务器 3U档×5客户×4服务等级 |
| onsite_rate_baseline | 10 | SV 产线×客户×国内/海外 |
| spare_aux_baseline | 35 | 国内+海外34国 |
| mgmt_cost_baseline | 10+10 | 售后(国内/海外) + 实施(国内=5/海外=50) |
| service_level_coeff | 6/7 | 服务水平系数 |
| failure_rate_baseline | 48 | 通用SV×8类部件×客户 |
| part_price | 56 | 备件单价（源表93，按 part_pn 去重） |
| bom | 59 | 示例机型(2U)整机BOM |
| man_day/travel/staff/capital | 46/6/72/1 | 人天/差旅/驻场/资金占用 |
| warranty_cost | 33 | 核算结果（验证基准，非建模实例） |

**API**
```
POST /api/ingest/preview?project_id=..
 {"ontology_id","object_type","source":{"kind":"field_map","records":[...]},"mapping":{"field_map":{k:k}}}
POST /api/ingest/candidates/{candidate_id}/approve?project_id=..
```

> ⚠ 两个**列偏移坑**：
> - 人天成本基线：**国家=列1 / 实施主体=列2 / 产品线=列3-5**（表头对齐≠实际列位）。
> - 人员驻场成本：**等级=列2 / 服务商从列3起**；且服务商表头是多行（如 `华夏\n（北京）`），**勿用 `split("\n")[0]` 截断**，否则会把「华夏(北京)/华夏(津鲁冀)」合并导致 lookup 歧义。

## 第 5 步｜定义能力（opl-expr + lookup/ref）

**✅ 目标**：把取数与公式固化为「可解释表达式能力」。

**🖥️ 平台侧操作/界面（截图说明）**
- **业务动作 → 能力 → 新建能力**：名称、显示名、对象类型、**表达式**。
- 表达式编辑器内可用：`lookup('对象', {维度:值}, '属性')`（回指基线实例）、`ref('cap_xxx')`（组上游能力链）、`if/if_null`、四则运算。
- 界面提供校验/发布按钮。

**本次构建的能力链**

```
cap_onsite_rate_d  = 现场服务率基线(产线SV×客户非BATZ×区域).rate × 年限系数
                     年限系数：3年=1.0；4年=×1.4；5年=×1.88
cap_labor_cost_e   = ref(cap_onsite_rate_d) × 售后人工成本基线(u_group×客户×区域×服务等级).unit_cost
cap_spare_aux_k    = ref(cap_onsite_rate_d) × 备件辅助成本基线(国家).unit_nd/unit_4h/unit_rma/unit_arma
cap_mgmt_cost_n    = ref(cap_onsite_rate_d) × 管理成本基线(客户×售后×区域).value
cap_total_o        = cap_labor_cost_e + spare_direct(F) + cap_spare_aux_k + cap_mgmt_cost_n
cap_ratio_s        = ref(cap_total_o) / machine_cost(R=37672)
```

**后续 5 个核算域能力**：`cap_man_day_cost`（人天×天数）、`cap_station_cost`（月成本×数量）、`cap_overseas_trip_cost`（差旅+服务商人天）、`cap_renew_cost`（平均价+备件辅助+×0.8%）、`cap_repair_cost`（人工+备件F+单件辅助+实施管理+资金占用）。

**API**
```
POST /api/capabilities?project_id=..  {name, object_type, expression, ...}
POST /api/capabilities/{cap_id}/publish  # 锁定版本（下游 ref 才能解析）
```

> ⚠ 三条必记：
> - ① `binds`（`a = this.x`）是**无条件预求值**，键缺失即 `MISSING_INPUT_ATTR`；可选属性要内联进 `if()`。
> - ② 表达式**最后位置**避免多行嵌套 `if()`，先 bind 变量、final 只放单层选择。
> - ③ **下游 ref 上游，必须先 `publish` 上游能力**，否则报 `REF_NOT_RESOLVED`。

## 第 7 步｜发布 MCP 并从 Agent 平台核验

**✅ 目标**：把本体通过 MCP 暴露给外部 Agent，并证明「从 agent 平台取数+核算」可用。

**🖥️ 平台侧操作/界面（截图说明）**
- **MCP 页 → 发布 Server**：选择本体 → 发布。界面显示端点 `/mcp/{project_id}` 与 tools 清单（`ontology_query / instance_get / capability_call / inference_trace / lineage_get / term_lookup / quality_health / action_invoke / alignment_* / fusion_*`）。
- **MCP 令牌**：项目静态 token（`POST /api/mcp/server/token?project_id=<pid>`）。
- 外部 Agent：`initialize`（带 `Mcp-Session-Id` 回传）→ `tools/list` → `tools/call capability_call`。执行返回 **溯源四要素**（能力版本+输入维度+lookup 命中+计算值），`execution_channel = mcp`。

**API**
```
POST /api/mcp/server/publish?project_id=<pid>&ontology_id=<oid>
POST /api/mcp/server/token?project_id=<pid>   → data.token
```

> ⚠ 发布后**首次调用可能返回 503「MCP 端点启动中」**，轮询重试（每 2s，1~3 次）即可。
> ⚠ REST 内部校验/问数**不需要**发布 MCP；但**对外/agent 验收必须发布 MCP**。

**核验结果（agent 平台实测）**：`cap_total_o` 返回 `209.8305397`，与结果表 **209.8305 精确一致**，`execution_channel=mcp`。

## 第 9 步｜源数据口径问题的处理

**✅ 目标**：识别并处理源表自身不一致（非建模/取数问题），**以基准表为准、不迁就错误公式**。

**本次发现的 3 处源数据口径问题（已写入报告第七节）**
| # | 问题 | 判定 |
|---|---|---|
| 1 | 驻场「北京」核算表月成本引用 `人员驻场成本!$C$10`（STR·**初级**=9000），与其标注「STR**中级**驻场」错位，应为 `$C$11`（STR·中级=13000） | 源表**引用行号偏移（差一行）**→ 按基准表=13000×12=**156000** |
| 2 | 单次维修 F 取备件成本「工厂=**1600**」单价（内存146/主板190），与 1100 厂（102/142）不同 | 反算确认 F 口径=工厂1600 |
| 3 | 海外（德国）现场服务率 D 4/5 年=0.3065/0.4115，**不从海外基数 0.2157 按 ×1.4/×1.88 递增**，反而等于国内基数 0.2189 递增值 | 源表口径矛盾，**需业务裁定** |

**🖥️ 平台侧处理（截图说明）**
- 在**建模页 → 数据字典**登记术语/同义词映射（地区→供应商、客户别名、F 口径→工厂1600/1100）。
- 在**实例导入页**用 PATCH（字段级）修正被截断/合并的取值（如保留供应商全名）。
- 在**能力编辑器**里按正确口径改表达式（如 `part_price` 按 `factory='1600'` 取数、`cap_station_cost` 明细）。

## 设计原则与坑点清单

### 设计原则（这次践行的四条）
1. **本体/实例 = 源表原值**：字段 1:1 保留，不截断、不合并、不去重丢失维度。
2. **数据字典 = 映射**：值归一化/别名/口径映射放字典（term/term_lookup），不改数据。
3. **结果对象只承载输入维度**：输出由能力 computed，目标值永不落实例。
4. **拒绝直接取数**：一切数值经 `lookup + 计算式` 产出。

### 坑点清单（实战高频）
| 坑 | 规避 |
|---|---|
| localhost → IPv6 挂起 | 用 `http://127.0.0.1:8000` |
| 导入显示值 vs 精确值 | 读单元格**原值**（0.2189 vs 0.218895427866865 曾致 ~0.01 元偏差） |
| 列偏移 | 逐列核对（人天表/驻场表列位≠表头视觉） |
| 多行表头截断 | 服务商/供应商名用全名，勿 `split("\n")[0]` |
| 下游 ref 上游未发布 | 先 `POST /api/capabilities/{id}/publish` |
| `binds` 无条件预求值 | 可选属性内联 `if()` |
| 尾位多行嵌套 if | 先 bind 变量，final 只放单层选择 |
| 空字段导入 | 用 `preview`（records dict）而非 `upload`（csv 空串） |
| F 备件直接成本 | 依赖 docx §4.3 精细模型 + 各厂商返修政策条件分支，非统一模板 |
| 海外 D 口径 | 源表矛盾，需业务裁定 |
