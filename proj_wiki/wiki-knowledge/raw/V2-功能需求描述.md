## 二、需求明细

### V2-01 数据字典 + 联邦查询解析

- **场景**：一个配件的 PN 编码，在 CRM 系统里字段为【PN】，在 PLM 里为【PN码】，在备件水库系统里为【PN_Num】。用户通过 AI 平台提问"给 xxx 客户更换一个 PN 码为 xxxxx 的备件，需要多久"。AI 平台经 MCP 访问本体平台，平台需将请求中的【PN码】在查 CRM 时写为【PN】、查 PLM 时写为【PN码】、查备件水库时写为【PN_Num】，分别检索后合并结果。对用户而言，只要统一用业务术语"PN码"提问，不管各系统字段如何存储，均通过本体平台的配置实现准确检索。另：AI 平台（LLM）生成查询请求时术语表达不稳定——可能写"PN码"、可能写"PN"、也可能写"PN号"，平台须对**输入术语做语义统一**，而不只是输出侧字段名统一（审核补充）。
- **现状**：外部 MCP 连接的 `maps_to_ontology.field_map`（`{系统字段: 本体属性id}`）已存在，但仅用于**入库方向**；平台没有"查询时访问外部系统"的路径（查询永远落在本地实例库/Fuseki 命名图）；field_map 是连接级配置，非统一字典资产。
- **需求**：
  1. **数据字典实体**：规范术语（绑定本体对象+属性，如 SparePart.PN码）＋ **术语同义词集（输入侧）**（如 PN/PN号/PN code/料号）＋ 系统侧字段绑定（按连接：CRM→PN、PLM→PN码、水库→PN_Num）＋ 可选值归一规则（去空格/大小写/编码格式）＋ **术语级权威来源系统（可选，审核补充）**：同一术语的值跨系统不一致时以哪个系统为准（与 V2-02 冲突策略"逐属性权威源"同概念、共用治理界面）；
  2. **存量 field_map 收敛**：各连接 field_map 改为引用字典（或从字典自动生成），同一术语别名单点维护；
  3. **查询时解析（含输入术语语义统一，审核补充）**：新增 MCP 查询工具（如 `term_lookup(term, value, systems?)` 或扩展 `ontology_query`）：入参术语**允许任意业务术语表达**（调用方为 AI 平台的 LLM，输出天然不稳定：PN码/PN/PN号 均可能出现）→ 术语归一（大小写/全半角/空格）→ **同义词精确匹配**（确定性优先）→ 未命中时**语义匹配**最近规范术语（embedding/LLM，候选限调用方授权范围内的术语）→ 字典解析各系统字段名 → 经现有 `mcp_client`（鉴权/超时/熔断复用）调各系统读工具 → 按规范键（PN 值）合并去重（**同键跨系统属性值不一致时：默认双值并存＋来源标记，已配置术语权威来源系统时按权威源取值——与 V2-02 冲突策略同源，不静默覆盖**），结果带"来源系统"标记与**术语解析路径**（输入词→规范术语、匹配方式、置信度）；
  4. **存疑升级与同义词治理（审核补充）**：语义匹配置信度低或候选模糊时**不猜**——返回候选列表＋置信度，由调用方判定；无候选则显式提示不覆盖；语义匹配结果经人工确认后**晋升为正式同义词**（后续走精确匹配路径，确定性且省语义匹配调用成本），形成"语义匹配→人工确认→晋升同义词"治理闭环；
  5. **查询成本护栏（审核补充）**：联邦查询须将分页/limit 参数**向下传递**至外部工具；外部工具仅支持全量拉取时，须声明拉取上限，并在预览时给出**成本提示**（返回规模/时延预估）。
- **验收**：
  1. 配置"PN码"→三系统字段后，查"PN码 xxxxx 的备件"三系统均命中并合并返回；
  2. 某系统未配置别名时**显式提示不覆盖**，不静默漏查；
  3. 入库方向与查询方向共用同一份字典配置，无双处维护；
  4. 外部工具仅支持全量拉取时，声明拉取上限且预览时给出成本提示（返回规模/时延预估）；
  5. `term_lookup` 传入"PN码"/"PN"/"PN号"任一表达均解析到同一规范术语，查询结果与传规范名一致，且结果含术语解析路径（输入词→规范术语、匹配方式、置信度）；
  6. 输入术语歧义（多个规范术语相近）时返回候选列表＋置信度，不自动选取；人工晋升同义词后，后续同词输入走精确匹配路径。
- **边界**：场景中"需要多久"属业务计算（库存判断+提前期规则），由 V2-04 承担；本条只解决"查得准"。
- **连接约定（审核决策）**：外部对接统一走 MCP Server——外部系统仅有数据库时，先包装为 MCP Server 再对接；平台不提供直连数据库（JDBC/SQL）适配器。

### V2-02 多本体对齐与融合

- **场景**：采购部门本体里的"供应商"对象与销售部门本体里的"供应商"对象是同一业务概念，但被两个本体独立建模（不同 ID、属性略有差异）。AI 平台要回答"该客户的供应商履约情况"时，需要关联两个本体的数据；当前没有任何机制声明"这两个对象是同一概念"，只能分别查询，结果重复且无法关联。且两部门建模人互不知晓对方本体的存在，**"谁来发起对齐"本身就是问题**（审核补充：由系统检测候选并提示，不依赖建模人主动发现）。
- **现状**：本体按 `urn:ontology:{id}` 命名图独立编译，无跨本体等价声明、无对齐/合并 API；唯一的 merge 是 enrich API 内部把上传材料合并进**同一**本体（`_merge_ontology`）。
- **需求**：
  1. **候选对齐检测与提示（审核补充）**：系统**周期批量扫描**（范围受 V2-06 共享等级约束）——仅对**评审建模人同时可见的两个本体**之间生成候选对，且**检测信号本身不得泄漏未共享本体**（私有/未共享本体不出现在任何人的提案中，其名称、对象名均不得出现在提示里）；自动发现**候选对齐对**（对象级＋属性级），产出**提案队列——只提示、绝不自动应用**；检测信号按强度排序：① **实例业务键重叠**（两对象实例 `stable_key` 键值相同，最强证据；键值比对同样只在可见范围内进行）；② **共同来源系统**（两本体从同一外部连接入库）；③ **名称/语义相似**（对象名/描述/属性名，复用 V2-01 语义匹配机制）；④ **结构相似**（属性集 名/类型/基数 重叠度）；每条提案展示证据与置信度，建模人**接受**→系统预填等价声明并进入冲突检测流程，**拒绝**→记为负样本后续扫描不再提示（证据显著变化才重新出现）；**手动创建声明保留为兜底通道**（检测漏掉的长尾由人发起，同样校验可见性规则）；
  2. **对齐（概念级）**：两本体间等价类/等价属性声明（owl:equivalentClass / equivalentProperty）＋ 冲突检测（属性值域、必填性、主键不一致时报出）；
  3. **实例对齐（个体级）**：同一现实个体在两个本体中是**不同记录**（不要求实例同一，只要求可解析对应）——
     - 自动：按等价属性上的业务键匹配（复用实例 `stable_key` 机制，键值相同=同一现实个体）；
     - 人工兜底：键对不上时显式 `owl:sameAs` 声明；
     - 对不上键的实例保持两条独立记录（带来源本体标记），实例对齐率作为治理指标展示；
  4. **融合（受控合并）与版本管理**：基于对齐声明把多个本体合并为**新本体**（原本体不可变）；融合本体具备**完整版本管理**（审核补充）：版本历史可查、版本间可对比（语义 diff）、**可回滚到任一历史版本**、**消费方（AI 平台/开放接口）可固定引用指定版本**（融合本体迭代与消费方稳定引用并存）；
  5. **实例数据模型与存储策略（审核修正，按数据源渠道区分）**：存储方式由**"有无可回源的源系统"**决定，不一刀切——
     - **源连接型**（外部 MCP 连接/业务系统）：**值不落地**。接入时归一化**只做一次**（field_map→本体属性、值归一规则，映射持久化、全部查询复用），平台只持久化**关系快照**：实例身份（stable_key/主键值）、对象类型、关系边、治理元数据（来源系统/导入批次/时间/血缘）；**内容读取联邦化、带权限**：任何非键属性值读取（含 owner 自查），平台**以访问者身份**（访问者→源系统凭据映射，复用 V2-14 身份联邦）经 mcp_client 请求源业务系统（复用 V2-01 联邦查询护栏：鉴权/超时/熔断/分页成本护栏），业务端按访问者权限按需返回，平台按键合并返回并带来源标记；
     - **上传型**（Excel/文档解析）：文件是**唯一数据载体**且无业务系统可回源，**值落地平台侧**（保留 MVP 存值方式：`JsonlInstanceStore` 全量存储对本渠道继续有效）；更新走重新上传/修订，挂导入批次与血缘；鉴权由平台自身执行（租户隔离＋用户角色）；
     - **跨本体查询（虚拟融合）**：本地关系快照上做 join（等价声明+实例键对齐）；内容获取分渠道——源连接型联邦回源按需取、上传型直接读本地存储值；合并去重返回；**实例不动、快照不动、源连接内容永远源端按需取**；
     - 可选**物化快照**（派生图，源本体变更后重建，明确标注"派生数据，非权威"）作为性能选项，须显式开启；
  6. **冲突策略**：同一键个体在两本体属性值不一致时**不静默覆盖**——默认双值并存+来源标记；可选**逐属性权威源**配置（每个等价属性指定以哪个本体为准，与 V2-01 字典"权威来源系统"概念同源，共用治理界面）；
  7. **对齐与融合的审核会签（审核补充）**：跨本体对齐声明/融合是**约束双方的语义承诺**，审核模式为**利益相关方会签而非上级裁决**（只有 owner 知道自己模型中"供应商"的语义边界）——跨 owner 的对齐声明与融合申请须**发起人之外全部源本体 owner 审批通过**（复用 V2-07 审批状态机：待审/通过/驳回/撤回，记录可审计，**一票否决**；申请材料=提案证据+冲突检测报告）；两本体 owner 相同时无需会签，可直接声明；owner 缺位（离职/转岗）时由**租户管理员代行**审核（留审计，不替代语义判断）；**共享等级（项目组/部门/公开）只授读可见，不携带审批权**——公开本体任何非 owner 不得单方面绑入等价关系。
- **验收**：
  1. 声明两个"供应商"对象等价后，键值相同的同一供应商跨本体查询返回**一条合并记录**（带双来源标记）；键值不同的实例返回两条；
  2. 同一键属性值冲突时：未配置权威源→双值并存+来源标记；已配置→按权威源取值且另一值可查；均不静默覆盖；
  3. 融合不改变原本体关系快照（实例集/键/关系不变，血缘保持到源系统）；源连接型实例内容永远源端按需取，平台不保存可发放的内容快照；上传型实例内容存本地（无源可回），同样不因融合而复制发放；
  4. 冲突检测能报出属性级冲突（值域/必填/主键）；融合产出带版本的新本体，版本历史可查可对比，可回滚到指定版本，消费方可固定引用指定版本；
  5. 系统对两个"供应商"对象自动生成候选对齐提案（展示键重叠/共同来源/语义相似证据与置信度）；接受后预填等价声明；被拒绝的提案后续扫描不再出现；
  6. 候选对仅在评审人同时可见的两本体间生成；不可见（未共享）本体的名称/对象名不出现在任何人的提案中（共享等级约束生效）；
  7. 跨 owner 对齐声明未获发起人之外全部源本体 owner 通过前不保存生效（一票否决）；同 owner 两本体声明直接生效；owner 缺位时租户管理员可代行审核（可审计）；公开本体不能被非 owner 绑定。

### V2-03 建模表单显式指定业务主键

- **场景**：建"服务产品成本"本体时，业务人员希望把产品对象的主键显式定为 `attr_product_code`；当前平台自动选"第一个必填 string 属性"，规则在界面上不可见、主键不可改，属性顺序排错导致主键漂移时只能删除重建（已填 ID/名称/约束全丢）。
- **现状**：`_backfill_object_fields()` 三级回退自动补齐；修改建议中 P1/P2（规则文案+实时主键标记+只读回显）已实现，**P3 显式指定未做**。
- **需求**：`OntologyObjectPatch` 增加 `stable_key` 字段允许 PATCH 修改；前端对象卡片增加"业务主键"下拉（选项=本对象 string 属性）并保留自动规则说明；后端校验显式值必须是本对象存在的属性 id，否则 422。
- **验收**：显式指定主键保存后持久生效；设不存在/非 string 属性返回 422 并提示。

### V2-04 计算能力与公式引擎（能力层）

- **场景**：「维保服务产品成本模型」本体已入库 2297 条实例，业务需要在**平台内**算出每个产品的各项成本、合计、占比（如 E(MA人工成本)=MA成本基线×现场服务率）；PN 更换场景中"需要多久"也需要按库存/采购提前期规则计算。公式目前散落在 Excel，靠 Agent 心算必然幻觉——公式必须是平台内可版本化、可溯源的一等资产。
- **现状**：`OntologyFunction` 为空壳元模型（无引擎/API/UI/MCP 工具）；《能力层元模型设计》v0.1（`docs/能力层元模型设计.md`）已给出元模型设计但未实现；`impact_inference` 仅 R1 引用回溯+R2 时间传导，不做数值传播。
- **需求**：按能力层元模型落地 `capabilities[]`（kind: derive/assert/act × implementation: expression/decision_table/script/external，3×4 矩阵按需提供格）；表达式求值引擎；公式定义/求值/溯源 API＋建模页 UI；MCP 计算工具；跨本体引用锁版本（引用方记 `capability_id+version`，被引用方升版不自动跟随，旧版本保留可追溯）；**渠道适配（审核补充，随 V2-02 实例数据模型）**：**上传型**直接读本地存储值求值、结果写回本地存储；**源连接型**输入值经**批量联邦读**获取（键集合→所需属性，受 V2-01 联邦查询成本护栏约束，执行前给成本提示），**派生值不写入权威实例存储、不写回源系统**——落为**派生图**（明确标注"派生数据，非权威"，与 V2-02 物化快照同概念，输入变更可重建，显式开启），后续查询/公式以标记数据身份参与；溯源"输入原值"记录联邦读自哪个系统、何时（fetched_at）。
- **验收**：
  1. 平台内定义 6 个成本公式并对 2297 个产品求值，结果与 Excel 口径一致（含容差）；
  2. 任一回算结果可回溯到「能力版本＋输入实例＋输入属性＋输入原值」；
  3. 删除被依赖的公式返回 422 并列出依赖方；draft 能力被 MCP 调用返回 403。

### V2-05 平台自身登录鉴权与 RBAC

- **场景**：平台推广到多部门使用后，建模人/审核人/只读查询人员都要登录同一平台；某部门建模人不应看到并删除其他部门的本体；当前任何人拿到内网地址即可操作，无登录、无角色。
- **现状**：MVP 明确不实现自身鉴权（Demo 阶段鉴权交外部）；无 RBAC。
- **需求**：登录鉴权（账号密码，预留 SSO 对接）；RBAC 角色模型（管理员/建模人/审核人/只读，可扩展）；资源级授权到项目/本体粒度。
- **验收**：未登录无法访问 API/页面；只读角色调写接口返回 403；授权在项目/本体粒度生效且可审计。

### V2-06 多租户、部门隔离与本体共享等级

- **场景**：公司 40+ 部门各自建本体与实例数据。数据平台团队接入后不能看到 A 部门本体的任何对象、实例与外部连接；部门管理员只管理本租户资源。当前 namespace 仅为轻量登记，无隔离。另：不同部门自建的本体模型相互隔离，建模人不希望内容被全公司可见，又需要按需开放给特定协作方（跨部门项目组/本部门/全公司）——**租户级"全有全无"的共享粒度不够，需要本体级共享权限等级**（审核补充，同时是 V2-02 候选检测的安全前提：检测提案不得泄漏未共享本体的存在）。
- **现状**：部门空间（namespace）注册表 CRUD 已有（8401dd5），但只是展示/登记，无数据隔离强制。
- **需求**：
  1. namespace 升级为租户边界：本体/实例/项目/外部连接/字典等数据按租户隔离；API 与 UI 全链路过滤；
  2. **本体共享权限等级（审核补充）**：每个本体独立共享等级，默认**私有**（仅建模人本人可见）；建模人可按需调整等级：**项目组共享**（指定到人，支持跨部门项目组）/ **部门共享**（本租户全员可见）/ **公开**（跨租户全员可见）；**共享等级只作用于语义模型（schema）：对象/属性/关系/定义，只读**（可见=schema 可见可查、不可见=404/403，与租户隔离语义一致）；**实例永不共享——共享不发放数据快照**（审核修正，按渠道区分）：**源连接型**实例的任何内容读取（含跨共享范围），平台**以访问者身份代查**源业务系统（访问者身份→源系统凭据映射，复用 V2-14 身份联邦），业务端按访问者权限鉴权、按需返回（可字段级），平台按键合并返回并带来源标记，实例可见性由源业务系统权限模型决定；**上传型**实例内容存平台侧（无源系统可回），共享同样不发放实例读取权：**内容读权限默认关闭（仅上传者本人可读）**，上传者**可显式指定开放范围**（指定到人/部门）；开放范围上限=本体共享等级可见范围（schema 不可见则内容天然不可读）；开放/收回操作留审计，与共享等级变更同级；等级变更须审计（谁、何时、从哪级到哪级）；共享只授 schema 只读，不授写权限（写操作仍走本租户资源）。
- **验收**：
  1. 租户 A 的用户在 API 与 UI 均不可见、不可访问租户 B 数据；
  2. 新建本体默认私有，他人不可见；建模人改为部门共享后本部门全员可见其 schema（只读）；项目组共享仅指定成员可见；公开后全员可见；
  3. 对不可见本体经 API 猜测资源 ID 访问返回 404/403；
  4. 共享等级变更可审计（谁、何时、从哪级到哪级）；
  5. **实例不共享**：本体被共享后，跨范围用户仅可见 schema；**源连接型**查询实例内容时平台以访问者身份代查源系统，返回数据由业务端按该访问者权限决定（同一本体、不同访问者返回范围不同）；**上传型**实例内容他人默认不可读，仅上传者指定开放到范围后该范围成员可读（上限为共享等级可见范围，跨范围不可读），开放/收回操作留审计；平台不直接发放其存储的数据快照。

### V2-07 变更审批流

- **场景**：ITBP 对已发布 MCP 的本体做破坏性变更（删属性、改值域）时不能直接生效，需提交部门负责人/知识管理员审批，通过后才重新发布；当前所有 schema 变更即时生效，外部 Agent 可能立即读到不一致结构。
- **现状**：仅实例入库有人工确认卡；本体/schema 变更无审批流。
- **需求**：审批节点定义（提交人/审批人角色）；审批态（待审/通过/驳回/撤回）；**驳回处理（审核补充）**：驳回后变更不生效、对外保持旧版本；审批人**必须填写驳回原因**并通知提交人；提交人可**修订后重新提交**（生成新审批实例，旧实例归档）或**放弃**变更；**审批粒度=变更集，不做逐条审批**（审批人部分不同意时，提交人剔除问题条目后重新提交剩余部分）；破坏性变更与发布联动（通过后生效/重新发布）；审批记录留痕可查（含驳回人/原因/时间）；审批流可扩展至**跨本体对齐/融合申请**（审批人=发起人之外各源本体 owner，会签规则见 V2-02，复用同一状态机与审计）；**两类审批的区别（审核补充）**：同一状态机同一审计，但为不同审批实例——**变更审批**是管理闸门（审批人=部门负责人/知识管理员等治理角色，上级审破坏性变更的合规性，单点否决）；**融合/对齐会签**是对等共识机制（审批人=发起人之外各源本体 owner，**一票否决**，各替自己的模型决策，不能由管理员代签，owner 缺位时由租户管理员代行并留审计）；**版本向下兼容性（审核补充）**：
  1. **自动兼容性判定**：发布时自动对新旧版本做语义 diff（复用 V2-02 版本对比机制），变更分级——**兼容**（新增对象/属性、新增可选属性、值域扩大、新增同义词）/**不兼容**（删除属性、类型变更、主键变更、值域收窄、对象合并/拆分）；
  2. **不兼容变更必须大版本＋强制审批**：自动判定结果作为本审批流输入（审批人可见"不兼容项有哪些"）；兼容变更以小版本直接发布；
  3. **先弃用后删除**：待删属性先标 @deprecated 发布，宽限期（可配，≥N 版本或 M 天）内保持可读，之后大版本才真删，给下游迁移窗口；
  4. **旧版本保持可用＋消费方版本固定**：新版本发布后旧版本服务（含 MCP 发布接口）保持可用；消费方（AI 平台/开放接口）可固定引用指定版本，未指定默认最新稳定版（与 V2-02 融合版本固定同构，统一版本引用机制）。
- **验收**：破坏性变更审批通过前对外不可见；驳回必须留原因（审批人/时间留痕），提交人可修订重新提交（新实例，旧实例归档）或放弃；审批以变更集为粒度，无逐条审批；审批记录可查询；兼容性判定自动标记不兼容项，不兼容变更未升大版本且审批通过不得发布；弃用属性宽限期内可读、期满后方可真删；新版本发布后旧版本接口仍可用，消费方版本固定生效。

### V2-08 细粒度血缘

- **场景**：AI 平台给出"该备件更换需 3 天"，业务追问数字怎么来的——库存值来自备件水库哪条记录、PN 字段映射自哪个源字段、"提前期"是公式能力哪个版本算的、上游实例哪批导入。当前血缘只到"数据来源=外部 MCP"粗粒度。
- **现状**：`_source` 元数据含 kind/connection_id/fetched_at/raw_ref 粗粒度标记；无实例（字段）级血缘。
- **需求**：实例级（及字段级）血缘：来源系统/源字段（经 V2-01 字典术语）/导入批次/转换规则（公式能力版本）/上游实例；提供血缘查询 API（并暴露为 MCP 工具），支持从任一实例向上游追溯的可视化；血缘元数据作为**治理数据**存平台侧（非业务内容，不受源连接型实例内容不落地策略影响，见 V2-02 实例数据模型）；**血缘模型针对入库侧**（快照入库/上传入库）；**联邦读内容**（逐请求、无导入批次）不持久化为实例血缘，由查询结果的来源标记＋术语解析路径（V2-01）与外部读取旁路日志（V2-10，可逐请求回放）共同保证可追溯。
- **验收**：任一新入库实例可追溯到源系统字段与导入批次；公式计算结果可追溯到输入实例原值与能力版本。

### V2-09 完整审计

- **场景**：多部门使用后，数据平台需回答"谁在何时删除了某本体的哪个属性、原值是什么、谁批准的回写"；当前 Postgres 审计日志为基础级别，操作类型与前后值覆盖不全。
- **需求**：全量操作审计（who/when/what/前后差异），覆盖建模/审批/入库/删除/回写/权限变更；日志不可篡改、不可经 API 删除；支持导出（CSV/JSONL）。
- **验收**：任一修改操作可按操作人+时间+对象检索并查看前后值；审计记录不可被任何接口修改删除。

### V2-10 JSONL append-only 旁路操作日志（V2 储备 P-04）

- **场景**：Action 回写失败重试 3 次、熔断打开期间有哪些调用被拒——运维需要从统一日志重建"当天实际打到外部系统的所有写操作"。当前执行记录分散在日志文件与 Postgres，难以回放。来源：《借鉴补丁建议-ontology-skill》P-04，wiki《范围与版本规划》已记录为 V2 储备。
- **现状**：MVP 有快照+SHACL 可回退，无统一旁路日志。
- **需求**：本体变更/Action 执行/外部读取统一记为 JSONL append-only 旁路操作日志（**非主存储**，主存储仍为 Jena+Neo4j+PG），统一 schema（actor/time/type/payload/result），支持回放与统计。
- **验收**：三类事件统一入日志；Action 回写可按天回放并与外部系统实际状态对账；日志 append-only。

### V2-21 数据健康度评估与质量趋势（数据治理指标）

- **场景**：数据平台团队把备件水库的库存数据接入本体，首批入库存在大量空值、业务键重复、脏值；建模改进后（补约束、字典归一、指定主键）需要**量化**地看到"数据真的变健康了"并向上汇报；同时 AI 平台被问"这个本体的数据质量现在如何"时能直接给出有依据的回答。
- **现状**：测量点已散落在管道中但无聚合/时序/对外——入库即跑 SHACL 校验（完整性/符合性）、实例均带 `stable_key`（唯一性）、`_source` 含 connection_id/fetched_at（时效性）、field_map 映射覆盖（覆盖性）；关系目标解析失败时**静默降级为字面量**（`rdf_sync.py` build_instance_triples，当前无统计）——恰是最该测而未被测的信号。
- **需求**：
  1. **指标体系**（核心四维零依赖可先发，扩展维度随依赖项后补）：
     - 完整性：键属性填充率、必填属性填充率、关系目标解析率；
     - 唯一性：stable_key 重复率；
     - 符合性：SHACL 违规率（按属性细分）、枚举值域命中率；
     - 时效性：按连接的数据新鲜度（fetched_at 距今天数）、陈旧数据占比（阈值可配）；
     - 扩展·一致性（依赖 V2-01/02）：字典映射覆盖率、跨系统同键冲突率、多本体实例对齐率；
     - 扩展·溯源率（依赖 V2-08）：血缘完整率；
  2. **两个评估时机**：
     - **接入时=批次健康卡**：preview/入库阶段输出本批指标（违规分布/键重复/填充率/新鲜度），展示在人工确认卡上辅助审核决策；
     - **建模后=质量趋势线**：每本体指标快照时序（基线=首次全量入库），量化建模改进前后的改善度；指标变化归因关联审计/配置变更记录（V2-09）；
  3. **暴露面**：质量看板 UI（本体级→属性级下钻）＋ API ＋ MCP 工具（AI 平台可查询）；
  4. **护栏原则**：
     - 指标是**观测与告警**（可选阈值告警），不是默认阻断（阻断仍是 SHACL 422 职责）；
     - 快照记录**指标口径版本**（约束/字典版本），比较区分"同口径"vs"跨口径"——新增约束导致违规率上升属"新暴露"，不得误报为数据变差；
     - 指标必须伴随规模（实例数/批次大小）展示，防止"删数据→分母变小→假改善"；
     - 与 V2-04 公式引擎严格分工：公式引擎算业务值，本项测数据资产健康度；
  5. **执行方式（随实例数据模型，审核修正）**：依赖键/关系的指标（唯一性、关系目标解析率、时效性）直接在平台本地**关系快照**上执行；依赖非键属性值的指标（完整性/填充率、SHACL 符合性）按渠道区分——**源连接型**改为**平台定义规则、源端执行回结果，或平台治理身份抽样执行**（不依赖平台侧全量内容存储）；**上传型**值存本地，直接在本地存储值上全量执行。
- **验收**：
  1. 构造含缺键/重复键/越枚举值的脏数据批次入库，健康卡输出对应指标异常并在确认卡可见；
  2. 新增约束/字典归一后，对应指标在趋势线上变化，且能关联到对应配置变更记录；新增约束导致的违规上升被正确标注为"口径变化"而非数据劣化；
  3. MCP 工具可返回指定本体当前健康快照（含实例规模）；
  4. 指标改善但实例数下降时，卡片展示"规模变化"标注。

### V2-11 schema 漂移停自动入库（快照自动更新）转人工，按键/非键分级（P1 遗留）

- **场景**：ERP 升级后，源端字段结构变了（新增字段、某字段类型变化、键属性源字段缺失）。源连接型实例平台侧只存**关系快照**、内容靠**联邦读**回源（见 V2-02 实例数据模型）：若继续按旧 field_map 自动更新快照，脏键/脏关系会污染快照（实例身份断裂）；联邦读按旧映射回源则类型不符/取不到值，外部消费者看到与 schema 不一致的数据；应停快照自动更新并提示人工复核映射。上传型无源系统，结构变化随重新上传走入库审核，不在本项范围。
- **现状**：PRD §4.7.4 要求"schema 漂移停自动入库转人工"，当前仅 `mcp_client` docstring 声明，未实现。
- **需求**：**检测渠道**（随实例数据模型调整）：①周期性 **schema 探测**（只拉源端字段结构、不拉数据，符合平台值不落地）；②关系快照更新（入库/CDC）时的字段结构比对；③**联邦读异常**（缺字段/类型不符）作为反馈信号；④**人工触发更新检查（审核补充）**：连接健康视图（V2-12）展示"上次 schema 检查时间＋距上次检查已过时长（xx 时 xx 分 xx 秒）"，用户可手动触发检查，复用周期检测同一管线与分级处置；已过时长超阈值（可配，默认=周期检测间隔的 N 倍）时页面醒目提示"检查已长时间未执行"，避免用户未察觉检查停摆、读取不到数据或不一致；与 field_map/对象约束比对后按严重度分级处置——**键属性漂移**（stable_key/主键源字段缺失或变更）：最高级，**停该连接关系快照自动更新**（原"停自动入库"）并立即告警；**非键属性漂移**：该属性标记"漂移"，其联邦读返回显式 null/错误标记（不静默通过），快照键/关系更新可继续，附告警；**未映射新字段**：不阻断，仅提示补映射；映射更新后恢复（快照自动更新/解除漂移标记）需**人工确认**。
- **验收**：模拟响应字段新增/类型变化/键字段缺失后分别触发对应分级动作（键漂移→停快照更新＋告警；非键漂移→属性标漂移、其联邦读显式标记返回）且给出漂移明细；映射更新+人工确认后恢复；漂移期间无脏键/脏关系入快照、漂移属性无静默通过；手动触发检查可用：检查完成后"距上次检查已过时长"归零，检出漂移触发与周期检测相同的分级动作；检查已过时长超阈值时页面醒目提示。

### V2-12 流式 CDC 与连接健康监控

- **场景**：备件水库实例实时变化（新增/状态变化/删除），AI 平台被问"PN码 xxxxx 现在有没有货"时，平台**关系快照**中的实例状态（新增实例未入快照、已删实例仍在快照）可能还停留在昨天入库；需要订阅外部系统变更，近实时刷新关系快照（内容值仍由联邦读回源，不在 CDC 范围）。
- **现状**：PRD 将"完整 CDC/流接入"放 V2；MVP 为手动触发/周期性读取。
- **需求**：外部源变更订阅（binlog/消息队列/增量接口，视各系统能力）；**通道边界与降级（审核补充）**：CDC 是**数据面独立通道，不走 MCP 协议**（MCP 只承担查询类调用与 V2-13 回写类调用，方向相反互不依赖），不要求外部系统提供"MCP 写服务＋主动推送"——binlog/消息队列为订阅模型、增量接口为平台高频游标拉取、webhook 真推送为可选能力不作硬性要求；外部系统仅有 MCP 读工具而无任何变更通道时，该连接**不启用 CDC**，实例新鲜度降级为"定时拉取＋联邦读"，连接健康视图明确标注"CDC 未支持"；CDC 事件携带的字段结构作为 schema 漂移检测的实时信号（即 V2-11 检测渠道②）；增量归化流水线（复用候选审核或低风险自动入库规则，与 V2-11 漂移检测联动；**只更新关系快照：实例键的新增/变更/移除与关系边，不同步内容具体值**，见 V2-02 实例数据模型）；时延与断流监控告警；**连接健康视图（审核补充）**：每个外部连接的健康状态页（成功率/时延/熔断状态/最近成功拉取时间/**上次 schema 检查时间＋距上次检查已过时长（xx 时 xx 分 xx 秒）＋手动检查触发按钮（审核补充，检测与分级处置见 V2-11）**），覆盖全部连接类型（手动拉取/CDC/联邦查询），阈值告警与断流监控共用。
- **验收**：外部实例变更后，关系快照（键/关系边）在承诺时延内（如分钟级）更新，联邦读可命中源端最新值；增量消费幂等、重复消费不产生重复实例；断流可告警；连接健康视图可查每连接成功率/时延/熔断状态/最近成功拉取时间，超阈值可告警。

### V2-13 回写风险分级（无条件自动回写）

- **场景**：成熟流程（如维保工单确认后自动在 CRM 创建服务工单）不希望每次回写都人工确认；但不同回写动作风险差异大，"一刀切"的自动/半自动开关不够安全——低风险动作人工确认是负担，高风险动作即使 AI 认为没问题也不能自动执行。回写动作需**分风险等级**决定执行方式，并留存签署证据供后续审计核验。
- **现状**：MVP 护栏为每次人工确认（human_required）；PRD 明确"无条件自动回写"后置 V2。
- **需求**：
  1. **Action 风险定级**：每个 Action 定级为 低/中/高 三档（Action 级配置，按操作类型给默认值建议：仅实例更新/幂等创建=低、外部实体创建/数据变更=中、删除/金额或合同相关/不可逆操作=高）；**定级调整须管理员操作并审计**，防止降级绕过护栏；
  2. **低风险=默认执行**：触发条件满足 → 前置校验（dry-run/映射校验）通过 → 自动回写，无人工确认；
  3. **中风险=AI 评估自动**：执行前 AI 生成**影响评估报告**（受影响系统/对象/实例/数据量、是否超出预期范围），同时满足以下三条才自动执行：① 评估**无预期外的外部影响**（影响范围限于目标系统与预期对象）；② 事件**原子性**（幂等键＋可回滚/可补偿）；③ 事件**完整性**（前置校验通过、数据完整）；评估报告随回写记录留存；**评估不通过或无法判定影响时升级人工确认**（存疑即升级，不自动执行）；
  4. **高风险=人工确认＋签署**：须人工确认，回写记录带**签署人标签**（签署人身份＋时间戳），用于后续审计核验；
  5. **共同护栏**：幂等键/指数退避/熔断在三级均生效；三级回写记录（含 AI 评估报告、签署人标签）统一进 V2-09 审计，可查、不可篡改。
- **验收**：
  1. 低风险 Action 触发后无人工介入完成回写；
  2. 中风险 Action 仅在 AI 评估通过时自动执行且评估报告可查；评估无法判定影响范围时升级为人工确认，不自动执行；
  3. 高风险 Action 无人工确认不可完成回写，记录含签署人标签（身份＋时间戳）；
  4. 幂等防重与熔断在三级均生效；任一历史回写可按级别/触发源/签署人检索审计。

### V2-14 复杂 Action 编排（含身份联邦）

- **场景**："更换备件"完整流程=查水库库存→缺货则在 PLM 建采购申请→采购完成后更新本体实例→通知 CRM。单 Action 只支持单步回写，需要多步编排（串行+条件分支）；同时平台调不同外部系统时各系统账号体系不同，需统一身份映射（平台身份→各系统账号/token）。
- **现状**：受控单 Action（dry-run/人工确认/幂等/熔断）已完整；无编排、无身份联邦（PRD V2 范围项）。平台已有 from-doc 逆向建模（文档→LLM 抽取→人工确认→落库）同构模式可复用；业务部门已按业务 SOP 沉淀了一批 skill。
- **需求**：
  1. **编排引擎**：现有单 Action 作为节点，支持串行/条件分支、失败重试/跳过/终止策略、编排状态可查；
  2. **编排编辑器（用户侧，可视化 no-code）**：三面板 DAG 编辑器——左侧**节点库面板**（Action 库已发布的受控单 Action，带入/出参字段说明＋控制节点：条件分支/人工确认/等待）；中间 **DAG 画布**（拖拽连线、起止节点、条件出口边标注分支条件、节点卡片标类型与风险级别）；右侧**属性面板**（选中节点参数映射，值类型仅三种：字面量/引用上游节点输出字段/触发上下文（操作者身份、事件数据）；失败策略重试/跳过/终止）；**条件节点=可视化规则配置**（字段＋运算符：=/≠/>/</包含/空/∈集合＋AND/OR 组合，无自由表达式）；顶栏配置触发方式（事件/手动/定时 cron 可视化）；**用户不可编写代码（审核补充，承接早期"编排不允许直接写代码"要求）**：页面无脚本/任意表达式配置入口，全部逻辑仅存在三种形态——Action 引用（能力已封装在 Action 库/MCP 工具）、字段映射、可视化条件规则；需要任意逻辑时先在**系统侧封装为新的 Action/MCP 工具**（代码在系统侧、管理员构建、审后发布），编排层只引用——理由：声明式 DAG 整体可审计、无运行时代码执行面、仅声明式节点可 dry-run 模拟、操作者为无编程背景的 ITBP；发布前 dry-run 模拟（样例数据，复用现有 dry-run 机制，逐节点输入/输出预览、风险节点展示待确认态）；
  3. **SOP 文档/skill 自动生成草稿**：上传 SOP 文档（md/Word）或导入 skill → LLM 抽取步骤/条件（skill 中的工具调用比自然语言更结构化，grounding 精度更高）→ 每步**语义 grounding 到 Action 库/本体对象/外部 MCP 工具**，生成编排**草稿**（DAG＋逐节点映射依据与置信度）；**定位是"预填草稿"而非直接发布**——草稿进同一编排编辑器人工审改后走与手动编排相同的发布通道；
  4. **生成防呆**：grounding 不到已配置能力/工具的步骤标记"能力缺口"显式列出（不静默变 no-op）；草稿中含高风险节点（V2-13 定级）的步骤自动挂人工确认节点，防生成通道绕过签署护栏；
  5. **AI 辅助生成局部编排（审核补充，第 3 条的局部化延伸）**：画布上选中局部区域（两节点之间/某分支下/空白槽位）→ 自然语言描述意图 → 生成**局部 DAG 片段**插入选区；**LLM 提示词严格限定可用操作内容**：节点仅限 Action 库**已发布** Action（名称/入参/描述）＋控制节点（条件分支/人工确认/等待）、条件仅限可视化规则运算符集、参数仅限**选中范围可见字段**（上游输出/触发上下文/本体属性）、输出必须是**结构化 DAG 片段**（节点＋边＋参数映射＋逐节点依据与置信度），代码/脚本/任意表达式/库外引用一律校验拒绝；片段进**草稿态**、走与第 3 条相同的审改/dry-run/发布通道，高风险节点自动挂人工确认、grounding 不到=能力缺口（同第 4 条防呆）；**边界声明**：AI 只在**构建侧**（生成/辅助），**不在执行侧**——运行时由确定性声明式 DAG 执行，LLM 不参与分支决策/工具选择/参数填充，执行路径可复现可审计（编排页内不引入公式引擎，复杂计算走 V2-04 系统侧受控组件）；
  6. **外部身份联邦**：平台用户→各外部系统凭据映射，凭据仍走本地加密存储；**不仅用于编排回写，也用于实例内容联邦读**（平台以访问者身份代查源系统，见 V2-02 实例数据模型）；
  7. （可选）**反向暴露**：已发布编排可暴露为 AI 平台的单个工具/skill（多步流程对 Agent 呈原子能力，Agent 是编排的调用方），形成 skill↔编排双向闭环。
- **验收**：
  1. 导入 SOP 文档/skill 后生成草稿，逐节点可见映射依据（匹配到哪个 Action、置信度）；无对应能力的步骤标记"能力缺口"而非静默丢弃；
  2. 草稿经人工审改发布后，执行行为与手动编排一致（同一引擎、同一审计）；
  3. 草稿中高风险节点自动携带人工确认节点；
  4. 多步编排按条件分支执行、各步状态可查；某步失败按策略重试/终止并保留现场；不同外部系统使用映射后的一致身份且可审计。
  5. **无代码红线**：编排页面无脚本/任意表达式配置入口，全部逻辑仅为 Action 引用＋字段映射＋可视化条件规则；现有 Action 无法表达的能力标记为能力缺口（不生成代码节点）；**AI 局部生成遵守同一红线**（提示词限定可用操作清单，库外引用/代码输出校验拒绝）。
  6. "SOP/skill→编排草稿"与"AI 局部生成"的**准确度验收须包含 golden dataset 评估**（见下 TODO），仅功能测试不通过。

### V2-15 开放查询接口：SPARQL / REST / GraphQL

- **场景**：公司 BI 与数据分析团队不走 AI 平台，希望直接消费本体数据：BI 工具按标准 SPARQL 接入、前端微应用按 REST 条件查询、移动端按 GraphQL 取数。当前平台只有自研 REST API 与 MCP Server。
- **现状**：FastAPI 自研 REST + MCP（streamable_http/sse）；无 SPARQL/GraphQL 端点。
- **需求**：SPARQL 端点（Fuseki 代理，按本体命名图隔离＋权限）；通用 REST 查询接口（按对象类型+条件+分页）；GraphQL（schema 由本体动态生成）；**数据边界（审核补充，随 V2-02 实例数据模型）**：开放接口暴露**本地图数据**=schema＋关系快照（实例键/类型/关系）＋上传型实例值；**源连接型非键属性内容不进入开放接口**（需要内容的走 MCP 查询工具的联邦读路径，或消费方直连源系统——BI 类批量消费无"每访问者→源端凭据"映射基础，不做带凭据的 SPARQL 代查）；返回字段带**来源标记**（schema/快照/上传值）；**上传型实例内容读权限遵循 V2-06 显式开放规则**（默认关闭、上传者显式开放、跨共享范围不可读）。
- **验收**：标准 SPARQL 客户端可查询指定本体命名图；REST/GraphQL 按对象类型条件查询并分页；三类接口均受 V2-05 权限约束；开放接口结果带字段来源标记，源连接型非键内容不返回（边界明确）；上传型内容默认不可读、开放后可读。

### V2-16 Fuseki 远程推理开关

- **场景**：本体规模增大（数千类/属性、上万实例三元组）后，本地 rdflib 推理慢且吃内存；需切换到 Fuseki 远程 OWL2-RL 推理（Jena 栈复用），本地推理保留为降级。
- **现状**：远程 DL 推理未启用（TASK_CHECKPOINT §18 遗留），推理走本地 rdflib。
- **需求**：推理引擎开关（local rdflib / Fuseki remote，配置化）；**推理图范围=本地命名图（schema＋关系快照＋上传型值三元组），源连接型非键内容不在推理图内（与 V2-02 实例数据模型一致）**；两模式推理语义与链路输出对齐；Fuseki 不可达自动降级本地并提示。
- **验收**：配置切换后推理链路（中文推断描述）两模式可比对一致；Fuseki 宕机自动降级；基准规模下远程推理时延优于本地。

### V2-17 SHACL 在 Jena 侧执行

- **场景**：实例批量入库量增大后，本地 pyshacl 校验耗时上升；需在 Fuseki 侧执行 SHACL（与推理服务同一 RDF 栈、形状版本一致），降低重复加载形状图的成本。
- **现状**：本地 pyshacl（已对齐 rdflib 7.6.0）；"SHACL 在 Jena 侧执行"为 TASK_CHECKPOINT §18 遗留项。
- **需求**：Fuseki SHACL 扩展执行路径；**校验范围=本地图数据：上传型实例值全量、关系快照键/关系；源连接型非键属性的约束校验不属于本项（走 V2-21 源端执行/抽样路径）**；违规明细输出格式与本地 pyshacl 统一（前端展示/422 details 复用）；Fuseki 不可达回退本地。
- **验收**：同一形状同一数据，两模式违规明细一致；Fuseki 不可达自动回退；大批量入库校验时延/吞吐达标（基准规模）。

### V2-18 MCP stdio transport 完整 JSON-RPC

- **场景**：本地 AI 客户端（Cursor/Claude Desktop/WorkBuddy）希望以 stdio 方式直连平台（本地进程桥）。当前平台自身 stdio transport 是 501 占位，靠外部桥接脚本（mcp_stdio_bridge_v2）转 http 绕过——桥是 workaround，平台应原生支持。
- **现状**：streamable_http + sse 双传输在线；`_stdio_invoke` 为 501 占位；桥接脚本在 v1.0.2 已加固但属绕行方案。
- **需求**：平台原生 stdio transport 完整 JSON-RPC（initialize / tools/list / tools/call），能力与 http 传输对齐（工具集、token 鉴权、发布态）。
- **验收**：标准 stdio MCP 客户端直连平台完成全工具调用；工具能力集与 http 传输一致；桥接脚本可弃用（保留兼容期）。

### V2-19 LinkML 外部模板网络加载预览

- **场景**：平台内置模板仅本地；ITBP 希望直接引用网络上的标准/社区 LinkML 模板（如供应链标准模板），预览其对象/属性/约束结构后实例化为本地本体。
- **现状**：本地模板库（LinkML 声明式管理已覆盖模板 CRUD+实例化）；网络加载为 PRD §6.8 P1 遗留。
- **需求**：网络 LinkML 模板加载（URL/registry）；结构预览（对象/属性/约束/许可声明）；一键实例化为本地可编辑本体。
- **验收**：指定网络模板可加载并预览结构；实例化后本地可编辑保存；离线环境优雅降级（提示+本地模板库）。

### V2-20 K8s 部署

- **场景**：平台推广到部门级使用后，需部署到公司 K8s 集群：后端多副本、Jena/Neo4j/Postgres 作为集群内状态ful 服务、数据持久化与弹性伸缩、镜像化升级回滚；替代当前本地一键启动（deps 自包含）+ Windows 安装包形态。
- **现状**：本地 Docker Compose/一键脚本 + NSIS 安装包（v1.0.2）；无 K8s 部署物。
- **需求**：K8s 部署物（Helm Chart 或 kustomize）；状态ful 组件（Jena/Neo4j/PG）StatefulSet+持久卷；后端无状态多副本；**后端本地文件型存储（如 JsonlInstanceStore 上传型值存储）多副本场景须迁移至集群共享持久存储（或收敛进 PG），保证副本间数据一致（审核补充，随 V2-02 实例数据模型）**；镜像构建与版本管理流水线。
- **验收**：K8s 集群部署后健康检查全绿（Jena/Neo4j/PG/后端/前端）；后端扩缩容 2+ 副本且数据不丢；镜像升级/回滚可平滑执行。

## 四、各需求典型操作流程（正常流，供测试用例生成）

**体例约定**：每条流程 = 前置条件 ＋ 编号步骤（`[角色] 操作 → 预期结果`）＋ 结束状态。仅覆盖**主路径**；异常/分支流不在此重复（见各需求"验收"条款）。角色：管理员、建模人（ITBP）、数据平台团队、业务人员、AI 平台（Agent）、系统（平台侧行为）。V2-05/06 的角色名以该需求定义为准。

### V2-01 数据字典 + 联邦查询（正常流）

- **前置**：CRM / PLM / 备件水库三个外部 MCP 连接已建立并通过连通性测试；本体中已建备件对象（SparePart）及"PN码"属性。
1. [管理员] 打开数据字典页，新建术语：规范术语"PN码"，绑定对象 SparePart ＋ 属性 attr_pn_code → 术语创建成功，归属可见
2. [管理员] 为该术语配置**同义词集**（PN/PN号/料号）与系统侧字段绑定：CRM→`PN`、PLM→`PN码`、水库→`PN_Num`，保存 → 字典生效，三个连接的原 field_map 自动收敛引用该术语
3. [管理员] （可选）配置值归一规则（去空格/转大写）并保存 → 规则随术语生效
4. [AI 平台] 经 MCP 调用 `term_lookup(term="PN号", value="xxxxx")`（术语用别名而非规范名）→ 调用受理
5. [系统] 输入术语归一（大小写/全半角/空格）→ 同义词精确匹配命中规范术语"PN码"（未命中则走语义匹配并带置信度）→ 按字典解析为三系统字段名，经 mcp_client 分别调用 CRM/PLM/水库读工具 → 三个系统均返回数据条目
6. [系统] 按 PN 值合并去重，输出统一语义结果，每条带"来源系统"标记与**术语解析路径**（PN号→PN码、精确匹配）→ 调用方收到合并结果
7. [AI 平台] 基于合并结果生成对用户的回答 → 用户获得跨系统检索答案
8. [管理员] 某新表达（如"部件编号"）首次经语义匹配命中"PN码"（带置信度）→ 人工确认晋升为正式同义词 → 后续该词输入走精确匹配路径
- **结束状态**：字典配置持久可查；联邦查询全过程（含术语解析路径）可审计；同义词集经确认持续完善。

### V2-02 多本体对齐与融合（正常流）

- **前置**：采购本体与销售本体各自建模"供应商"对象，且两侧均已入库实例（含"供应商编号"属性值）；两本体从同一外部连接入库；两本体已被各自建模人设为**部门共享**（或项目组共享），且两位建模人相互可见。
1. [系统] 周期扫描（**仅扫描评审人可见范围内本体**，未共享给评审人的本体不进入扫描）发现候选对"采购本体.供应商 ↔ 销售本体.供应商"（证据：实例键重叠 1200/1380、共同来源系统、名称语义相似度高）→ 生成对齐提案卡（对象级＋属性级候选，带置信度）
2. [建模人] 打开提案卡，查看证据与冲突预览 → 接受 → 系统预填等价类声明
3. [建模人] 确认等价属性（供应商编号 ↔ 供应商编号）→ 提交对齐声明
4. [系统] 执行冲突检测（值域/必填/主键）→ 无冲突，冲突检测报告随申请材料生成
5. [系统] 两本体分属不同 owner → 声明进入审批流（复用 V2-07 状态机，待审）；若两本体同 owner 则直接生效，跳过本步
6. [销售本体 owner] 审阅提案证据与冲突报告 → 通过 → 声明保存并生效（驳回则声明不保存，通知发起人可撤回/重新提交）
7. [系统] 按等价属性业务键自动实例对齐：键值相同的实例标记为同一现实个体 → 对齐关系建立并可查询
8. [AI 平台] 提问供应商履约情况 → 跨本体查询经对齐关联两侧实例
9. [系统] 键值相同的供应商返回**一条合并记录**（双来源标记）；键值不同的实例返回两条独立记录 → 查询结果正确
10. [建模人] （可选）触发融合：基于对齐声明生成新本体（统一语义）→ 融合申请同样经发起人之外各源本体 owner 通过 → 新本体带版本创建，原本体不可变；融合本体版本历史可查/可对比，可回滚到指定版本，AI 平台可固定引用指定版本
11. [建模人] （可选）为某等价属性配置权威源 → 后续同键冲突按权威源取值
（另一入口：纯手动——建模人在对齐页自行选择两对象声明等价，同样校验可见性规则与跨 owner 会签规则，后续流程相同；建模人拒绝的提案记为负样本，后续扫描不再提示）
- **结束状态**：跨本体联合查询可用；融合本体具备完整版本管理（历史/对比/回滚/版本固定引用）；检测受共享等级约束，候选对接受/拒绝与跨 owner 会签记录均可审计。

### V2-03 显式指定业务主键（正常流）

- **前置**：服务产品成本本体处于编辑态，产品对象含 string 属性 attr_product_code。
1. [建模人] 打开产品对象卡片，展开"业务主键"下拉（选项=本对象 string 属性）→ 当前自动主键回显可见
2. [建模人] 选择 attr_product_code，保存 → PATCH 携带 stable_key 成功
3. [系统] 校验（必须是本对象存在的 string 属性）通过 → 保存成功提示
4. [建模人] 刷新页面 → 主键仍显示 attr_product_code（持久生效）
5. [数据平台] 入库新实例 → 实例按显式主键参与匹配/去重
- **结束状态**：主键显式持久生效，自动规则说明仍展示。

### V2-04 计算能力与公式引擎（正常流）

- **前置**：维保成本本体已入库 2297 条产品实例（**上传型，值存平台侧**）；能力层元模型已落地。
1. [建模人] 打开能力页，新建能力：kind=derive × implementation=expression，定义" E(MA人工成本)=MA成本基线×现场服务率 "，绑定输入属性 → 能力草稿创建成功
2. [建模人] 保存公式并**发布**为版本 1 → 能力进入 published，版本号 v1 可引用
3. [建模人] 在产品对象上触发"对全部实例求值" → 系统按公式遍历 2297 实例
4. [系统] 逐实例求值并持久化结果（派生值，本地存储），同时记录溯源：能力 v1 ＋ 输入实例 ＋ 输入属性 ＋ 输入原值 → 2297 条结果生成
   （源连接型变体：输入值经批量联邦读获取（执行前成本提示），结果落**派生图**（标"派生数据，非权威"），不写入权威实例存储）
5. [业务人员] 查看求值结果，与 Excel 口径比对 → 一致（含容差）
6. [业务人员] 点击任一结果查看溯源 → 展示"能力版本＋输入实例＋原值"链路
7. [AI 平台] 经 MCP 计算工具对指定产品求值 → 返回同一口径结果
- **结束状态**：6 个成本公式全部求值并与 Excel 一致；所有结果可溯源到能力版本与输入原值。

### V2-05 登录鉴权与 RBAC（正常流）

- **前置**：已配置账号与角色（管理员/建模人/审核人/只读）。
1. [用户] 未登录访问平台页面 → 重定向到登录页
2. [用户] 输入正确账号密码登录 → 登录成功，按角色加载可见范围与操作权限
3. [只读用户] 打开本体列表 → 仅可见已授权的本体，无编辑入口
4. [只读用户] 调用建模写接口（或直接调 API）→ 返回 403
5. [建模人] 在本项目内创建并保存本体 → 成功
6. [管理员] 调整某用户的角色授权 → 变更即时生效，该用户权限随之变化
- **结束状态**：登录与 RBAC 全链路生效，越权操作被拒。

### V2-06 多租户、部门隔离与共享等级（正常流）

- **前置**：已注册两个租户（部门）A、B；各自有成员账号。
1. [租户A建模人] 创建本体 A1 并入库实例 → 数据归属租户 A，共享等级默认**私有**
2. [租户A同事] 打开本体列表 → A1 不可见（私有，仅建模人本人可见）
3. [租户B用户] 登录打开本体列表 → 仅见租户 B 数据；直接经 API 猜测资源 ID 访问 A1 → 返回 404/403（不可访问）
4. [租户A建模人] 将 A1 共享等级改为**项目组共享**，指定 3 人（租户A 2 人＋租户B 1 人）→ 授权生效，等级变更留审计
5. [被指定的租户B成员] 打开本体列表 → A1 schema 可见（只读）；未被指定的租户B成员仍不可见
6. [租户A建模人] 将 A1 改为**部门共享** → 租户 A 全员可见其 schema（只读）
7. [被指定的租户B成员] 查询 A1 实例内容 → 平台以该成员身份代查源业务系统 → 业务端按其权限按需返回（非平台存储快照）；不同权限成员返回范围不同
8. [上传者] A1 含上传型实例（Excel 条目）→ 他人默认读不到其内容（默认关闭）；上传者指定开放给 2 名部门成员 → 该 2 人可读、其余人不可读，开放操作留审计
- **结束状态**：API 与 UI 全链路租户隔离；本体 schema 可见范围由共享等级决定，源连接实例内容由源系统按访问者权限返回，上传型实例内容默认关闭、由上传者显式开放，相关变更均可审计。

### V2-07 变更审批流（正常流）

- **前置**：本体 O 已发布 MCP（v1）；已配置审批角色（部门负责人）。
1. [ITBP] 对已发布本体 O 做破坏性变更（删除某属性），提交 → 系统自动兼容性判定（语义 diff）标记"不兼容：属性删除" → 变更进入"待审批"（不兼容变更须升大版本 v2），未生效
2. [系统] 通知审批人（推送/站内）→ 审批人收到待办
3. [审批人] 查看变更 diff（删了什么、影响哪些实例/下游、不兼容标记）→ 信息完整
4. **驳回分支**：[审批人] 点击"驳回"并填写原因（如"该属性仍有下游依赖"）→ 变更不生效、对外保持 v1；[ITBP] 收到通知，剔除问题条目修订后重新提交（生成新审批实例，旧实例归档），或放弃该变更；驳回全程留痕
5. **通过分支**：[审批人] 点击"通过" → v2 生效
6. [系统] 触发重新发布，外部 Agent 读到新结构 → 发布成功，审批记录留痕；v1 接口保持可用（旧版本不下线）
7. [消费方] AI 平台固定引用 v1 → 仍按 v1 结构正常读取（版本固定生效）
8. [ITBP] 另一属性改为先标 @deprecated 发布 → 宽限期内照常可读，期满经后续大版本真删（先弃用后删除）
9. [ITBP] 在审计/审批记录中查看审批历史 → 提交人/审批人/时间/结果（含驳回原因）可查
- **结束状态**：破坏性变更经兼容性判定＋审批后生效，全程留痕；驳回路径留原因、可重新提交或放弃；旧版本保持可用，消费方版本固定生效。

### V2-08 细粒度血缘（正常流）

- **前置**：备件实例已入库（来源=水库，经 V2-01 字典 PN 码）；已有公式计算结果（V2-04）。
1. [用户] 选中某备件实例，请求"血缘" → 血缘面板打开
2. [系统] 返回实例级血缘：来源系统=水库、源字段=`PN_Num`（字典术语 PN 码）、导入批次、fetched_at → 链路展示
3. [用户] 选中某公式计算结果，请求血缘 → 返回计算血缘：能力版本 ＋ 输入实例 ＋ 输入属性 ＋ 原值 → 链路展示
4. [AI 平台] 经 MCP 血缘工具查询指定实例上游 → 返回结构化血缘
- **结束状态**：任一实例/计算结果可向上游追溯到源系统字段与输入原值。

### V2-09 完整审计（正常流）

- **前置**：多用户已执行建模/入库/删除/回写/权限变更操作。
1. [数据平台] 打开审计日志，按操作人＋时间＋对象类型筛选 → 命中相关操作
2. [数据平台] 查看某"删除属性"记录 → 展示 who/when/what ＋ 前后值差异
3. [数据平台] 导出为 CSV/JSONL → 文件内容与页面一致
4. [任意角色] 尝试经 API 修改/删除某条审计记录 → 被拒（不可篡改）
- **结束状态**：全量操作可检索、可导出、不可篡改。

### V2-10 JSONL 旁路操作日志（正常流）

- **前置**：平台运行中，已发生本体变更 / Action 执行 / 外部读取。
1. [系统] 将三类事件按统一 schema（actor/time/type/payload/result）追加写入 JSONL 旁路日志 → 日志文件追加（append-only）
2. [运维] 打开日志回放工具，选定某一天 → 重建当日 Action 回写操作序列
3. [运维] 将回放结果与外部系统当日实际状态对账 → 一致
4. [运维] 校验日志完整性（append-only/哈希链）→ 通过

6. [系统] 快照更新正常、联邦读恢复 → 漂移期无脏键/脏关系入快照、漂移属性无静默通过

### V2-13 回写风险分级（正常流）

### V2-14 复杂 Action 编排（正常流）

- **前置**：身份联邦已配置（平台用户→CRM/PLM 凭据映射）；Action 库已有单 Action（查水库库存/PLM 建采购申请/更新实例/通知 CRM）；一份"更换备件"SOP 文档就绪。

2. [建模人] 审阅草稿：节点映射无误、无"能力缺口"（若有缺口，先补 Action 或改为人工任务节点）→ 在编辑器调整条件分支与失败策略 → dry-run 模拟通过 → 发布
   （另一入口：纯手动——从 Action 库拖拽节点组装 DAG，同一编辑器、同一发布通道）
3. [系统/事件] 触发编排（事件或手动）→ 编排启动
4. [系统] 按条件分支逐步执行（若缺货→PLM 建采购申请分支），每步状态（运行中/成功）可查询 → 各步依次成功
5. [系统] 某步失败 → 按配置策略重试/跳过/终止，保留现场
6. [数据平台] 审计查看编排执行 → 各外部系统使用映射后的一致身份，可查
- **结束状态**：自动生成的草稿与手动编排走同一引擎执行，全程状态可查、身份可审计。
