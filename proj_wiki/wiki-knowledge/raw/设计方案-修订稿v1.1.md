## 1. 定位、用户与痛点

**目标用户**：公司内部 40+ 部门，由各部门的 **ITBP** 负责在本平台搭建本部门本体模型，并发布/接入 MCP 服务。

**核心痛点**：智能体平台中大模型幻觉严重、数据使用逻辑链路不可信；目标依靠本体做**语义底座约束大模型**。

**执行能力分阶段（修订）**：
- **MVP（本版范围）**：静态建模 + 查询；可通过 **MCP Client** 读取 CRM/SAP 等外部含鉴权数据平台的实时数据（新增）；本体内置 Action 并可**受控回写**外部平台（新增，需人工确认）。
- **二期**：扩展无条件自动回写、多租户、审批流、细粒度血缘、完整审计、RBAC。

**服务范围**：现阶段优先作为**大模型 Agent 语义底座**；远期扩展数据治理、BI；不做业务系统开发。

**现状与约束（影响设计）**：
- 数据源：ERP/CRM/PLM 多套系统、多数据库，字段不统一、同义异写、填写不一致，**数据质量参差不齐**。
- 团队：有少量知识工程背景人员；当前开发仅**单人 + AI 辅助编码**，人力后续按需申请，周期未定。
- 核心风险：① 业务门槛高，ITBP 上手难、见效慢；② 工程风险，AI 生成代码质量不可控、维护成本高。

**软件形态（明确）**：MVP 为**本地网页服务（Local Web Service）**——Python 后端（建议 FastAPI）+ 浏览器前端（localhost 访问），Jena / Neo4j / Postgres(pgvector) 同机部署；**非桌面应用（Electron 类）、非云 SaaS**。MVP 建议用 **Docker Compose** 一键拉起全部组件（单机即可），V2 再迁移 K8s。该形态既满足「本地单人模式」，又能让发布的 MCP Server 被外部智能体平台网络调用。

## 2. 范围定义（采纳优化 1、优化 3、优化 6、优化 8）

### 2.1 MVP 范围（本地单人模式，修订）

**MVP 必须包含**：
- 单人本地模式；手工建模、逆向建模、Schema 约束配置、混合建模 4 种建模方式
- 概念约束、业务关系推导推理能力
- 业务文档、数据记录自动归化成本体实例（**须经人工审核**，见 §4.3）
- 支持自定义 LLM endpoint 接入
- UI 图形化发布 **MCP Server** 服务，可在外部智能体平台注册调用（查询/推理工具，见 §4.6）
- **【新增】UI 配置并接入外部含鉴权数据平台的 MCP Server（MCP Client），读取外部数据归化成本体实例（见 §4.7）**
- **【新增】本体 Action 受控执行：可对外部平台进行数据回写（人工确认 + 幂等 + 执行日志，见 §5.3）**
- UI 可视化：本体关系、知识图谱、推理链路展示
- 预置行业本体模板 + 网络动态加载预览外部模板
- 本体版本快照、本体一致性（SHACL）校验、推理链路追踪

**MVP 明确不包含（后置 V2.0）**：
- 多租户、部门/工作组隔离、变更审批流、细粒度血缘映射、完整审计日志、RBAC 权限
- **无条件自动回写**（MVP 仅支持人工确认模式下的受控回写）
- Action 执行引擎的复杂编排（并行/条件分支工作流）、外部系统流式 CDC、多平台统一身份联邦

> 理由（优化 1 + 优化 8）：本地单人模式无多人协作审批需求；但「能读外部真实数据、能把 Action 结果回写」是验证本体业务价值的必要闭环，缺一则本体只是离线建模工具，拿不到业务侧真实反馈。故把 MCP 双向接入与受控回写前置，治理与安全强护栏（凭据加密、人工确认、幂等）在 MVP 即落地，避免回写变成"裸写外部系统"的高危操作。

### 2.2 二期 / 远期范围

- **V2.0 服务端版本**：K8s 云原生部署；多租户部门/工作组共享与隔离；全套企业治理（审批流、血缘、审计、细粒度权限）；Action 执行引擎增强（复杂编排、无条件自动回写、统一身份联邦）；外部系统流式接入；扩展 SPARQL/REST/GraphQL 接口；对接数据治理基础能力。
- **V3.0 远期**：BI 可视化消费；本体资产市场与模板库共享；更多数据接入适配器。

## 3. 总体架构（采纳优化 2、优化 4、优化 6、优化 8）

### 3.1 双层建模架构（优化 2，不变）

底层严格遵循 W3C OWL2-RL / SHACL 保证推理；上层面向 ITBP 封装业务层模型，**屏蔽复杂语义术语**。

- **业务层（ITBP 可见）**：仅接触「业务对象、业务属性、业务关系、业务约束、关联外部数据源」，**不直接暴露** Class、ObjectProperty、TBox/ABox、DL 公理等原语。
- **标准层（平台内部）**：平台自动将业务层翻译为 OWL/RDF，做存储、推理、MCP 输出。

### 3.2 七层通用架构裁剪（修订）

| 层 | 本平台落地 |
|---|---|
| L1 数据接入 | MVP：**① 逆向建模从数据库表导入 Schema；② 文档解析生成候选实例；③【新增】外部 MCP 数据源接入（带鉴权读取，映射归化）**；完整 CDC / 流接入放 V2 |
| L2 本体建模层 | 自研上层业务 UI，底层复用 Jena / WebProtégé 的本体 API |
| L3 知识存储层 | 混合存储：Jena 处理 TBox 本体 Schema；Neo4j 存储 ABox 实例；pgvector 存向量 |
| L4 推理计算层 | Jena 提供 DL 推理、SHACL 约束校验；MVP 实现推理链路溯源 |
| L5 服务消费层 | MVP 实现 **MCP 双向**：Server 端（对外暴露本体能力）+ Client 端（对内接入外部数据平台、支撑 Action 回写）；SPARQL/REST 后置 V2 |
| L6 应用构建层 | MVP 仅内置 UI，不提供低代码应用构建 |
| L0 治理安全（横向切面） | MVP 仅保留版本快照、一致性校验；**【新增】凭据加密存储、回写人工确认/幂等/执行日志**；审批、多租户、审计全 V2 落地 |

### 3.3 混合存储设计（优化 4，不变）

1. **TBox 本体 Schema（模式层）**：使用 **Apache Jena** 做 OWL 解析、SHACL 校验、DL 推理；以**独立 HTTP 服务**方式部署，Python 后端通过 HTTP 调用，避免 Java/Python 深度混编。
2. **ABox 实例数据（实体、实例关系）**：**Neo4j 社区版**，利用图数据库做高性能实例查询、可视化展示。
3. **向量索引**：对接 **pgvector**，用于文档归化实例的向量检索。

> 注意：Neo4j 社区版不提供原生 OWL-DL 推理；推理逻辑统一交给 Jena 服务，Neo4j 只承担实例存储、图遍历、可视化。

## 4. 功能模块设计

### 4.1 本体建模（采纳优化 2 业务层封装，不变）

- 4 种建模方式：手工建模、逆向建模、Schema 约束配置、混合建模。
- 上层业务友好 UI；底层映射 W3C OWL2-RL + SHACL。
- 类层次、对象/数据属性、约束在业务层以「对象/属性/关系/约束」语义呈现，平台翻译为 OWL 原语。

### 4.2 推理与校验（不变）

- 概念约束、业务关系推导推理能力；推理链路**可追溯可视化**；SHACL 一致性校验；本体版本快照（支持历史回溯）。

### 4.3 实例归化流水线（采纳优化 5，不变）

**MVP 流水线**：源数据（表 / 文档 / **外部 MCP 读取结果**）→ LLM 自动归化或字段映射生成**候选实例** → **平台人工审核 UI** → 审核通过后写入本体实例库。

- **禁止 LLM 输出直接落库**。
- 外部 MCP 读取的结构化数据可信度高于 LLM 自由生成，可走「字段映射 + SHACL 强校验」路径；但**首次接入某外部源或映射规则变更时，仍须人工确认卡**（见 §4.7）。
- 支持自定义 LLM endpoint；逆向建模产出的 Schema 允许人工二次修正。

### 4.4 可视化（不变）

- 本体视图、知识图谱视图、推理链路视图三类可视化。

### 4.5 模板管理（不变）

- 预置行业本体模板随安装包附带；新建本体时可网络动态加载预览外部模板；用 LinkML 做模板声明式管理。

### 4.6 MCP 服务（采纳优化 6，修订为双向）

- **定位**：MCP 是**本体与外部世界之间的双向桥梁**。
  - **Server 端（向外暴露）**：把本体模型**自动生成**工具，供外部智能体平台注册调用：
    1. 本体语义查询工具（`ontology_query`）
    2. 获取推理解释链路工具（`inference_trace`）
    3. （可选）实例读取工具（`instance_get`，受本体权限约束）
  - **Client 端（向内接入，新增）**：作为 MCP 客户端连接外部数据平台的 MCP Server，读取数据并支撑 Action 回写（见 §4.7、§5.3）。
- **实现方式（修订 C4）**：原定稿称「开源组件原生不支持 MCP，需自研封装」。现已有官方 **MCP Python SDK**（`modelcontextprotocol/python-sdk`，MIT）与 `FastMCP` 封装，MVP 应**复用官方 SDK** 实现 Server + Client，避免从零自研传输层/协议编解码，降低 AI 生成代码的协议错误风险。
- 注：Server 端工具的能力集仍由本体 Schema **自动生成**；Client 端连接配置由用户在 UI 配置。

### 4.7 外部数据源 MCP 接入（新增模块，对应优化 8 / C1 / C3）

> 解决「MVP 读取外部含鉴权数据平台」需求。平台作为 MCP Client，连接外部数据平台提供的 MCP Server。
> **前置条件（已确认）**：外部 MCP Server 由对接方**已提供**，平台按对方暴露的 transport（`stdio` / `streamable_http`）与工具列表接入，**不假设自建**；兼容性上同时支持两种 transport。

**4.7.1 连接配置（Connection）**
每个外部数据源在平台内以一条「连接配置」描述，建议 JSON 结构（UI 表单落库）：

```json
{
  "connection_id": "crm-sf-mcp",
  "display_name": "销售易 CRM（MCP）",
  "transport": "streamable_http",
  "endpoint": "https://mcp.crm-vendor.com/mcp",
  "auth": {
    "type": "oauth2_client_credentials",
    "token_url": "https://idp.crm-vendor.com/oauth/token",
    "client_id": "${CRM_CLIENT_ID}",
    "client_secret": "${CRM_CLIENT_SECRET}",
    "scopes": ["mcp.read", "mcp.write"]
  },
  "tool_allowlist": ["query_account", "upsert_contact"],
  "maps_to_ontology": {
    "object_type": "Customer",
    "field_map": { "account_name": "name", "industry": "industry" }
  },
  "read_schedule": "manual"
}
```

**4.7.2 鉴权方式（外部平台负责鉴权；本体平台 Demo 不实现自身登录鉴权）**
按用户决策，**本体平台 Demo 版本不实现自身的用户登录 / 鉴权层**（本地单人模式，信任本机用户）；鉴权职责交由外部数据平台。但平台作为 MCP Client 调用外部 MCP Server 时，仍需持有并发送外部平台要求的凭据：
- `bearer_token` / `api_key`：静态令牌，Demo 以**本地配置文件 / 环境变量**管理（建议 `chmod 600` 且加入 `.gitignore`）；生产环境应改为 KMS / 密钥管理。
- `oauth2_client_credentials`：客户端模式（server-to-server，无人工交互），平台用 `client_id/secret` 换 `access_token` 并缓存，过期自动刷新。**不采用 authorization_code 等需人工浏览器登录的流程**（MVP 无多用户会话体系）。
- `basic`：仅本机/内网 legacy 系统按需支持。
> 注意：即使 Demo 不强制加密，仍**禁止在日志中打印凭据明文**；加密落盘（cryptography.Fernet）作为**建议项**保留，生产必须启用。

**4.7.3 读取与归化流程**
外部 MCP Server 工具调用 → 原始结构化数据 → 按 `field_map` 映射为候选本体实例 → **SHACL 校验** → 进入人工确认卡（首次接入/映射变更/高风险对象）或自动入库（映射已校验且低风险）。读取结果可写入 Neo4j 实例库并打「数据来源 = 外部 MCP」溯源标记。

**4.7.4 健壮性（建议做，MVP 至少兜底）**
- 连接健康检查 + 超时（默认 10s）+ 失败重试（指数退避，最多 3 次）。
- 外部工具返回 schema 漂移（字段缺失/类型变化）时，停止自动入库并提示人工复核。
- 凭据失效（401/403）时阻断读取并告警，禁止静默降级为无鉴权。

### 4.8 可视化（见 §4.4，补充）

知识图谱视图应可区分「本体内部实例」与「外部 MCP 来源实例」的溯源着色，辅助审核。

## 5. 技术选型与组件约束

### 5.1 复用策略（不变）

尽可能复用开源组件，不自研核心语义逻辑；平台为公司内部自用，不排斥 GPL 强传染协议组件（如 Neo4j 社区版）。

### 5.2 组件清单（可复用，许可允许自用二次开发，修订）

| 组件 | 许可 | 用途 | 备注 |
|---|---|---|---|
| WebProtégé | BSD-2-Clause | 本体建模核心参考 | 前端 GWT 老旧，复用后端 API、前端自研业务友好 UI |
| Apache Jena | Apache 2.0 | OWL 解析、RDF 存储、SPARQL、SHACL 校验、推理 | 独立 HTTP 服务，Python 仅 HTTP 调用 |
| ROBOT | BSD-3-Clause | 本体格式转换、一致性校验 | 可集成做 CI 校验 |
| LinkML | MIT/CC0 | YAML 声明式本体，适合模板管理 | — |
| Neo4j Community | GPLv3 | ABox 实例存储与图可视化 | 内部自用可接受；不依赖其做 OWL-DL 推理 |
| pgvector | PostgreSQL 扩展 | 文档归化实例的向量检索 | — |
| **MCP Python SDK（`modelcontextprotocol/python-sdk`）** | **MIT** | **MCP Server + Client 实现（新增）** | **复用官方 SDK，MVP 不自研传输/协议层；`FastMCP` 可作 Server 端便捷封装** |
| **cryptography** | **Apache-2.0 / BSD-3-Clause** | **凭据加密存储（建议项，生产必做）** | **Fernet 对称加密；Demo 可不启用，以本地 env/配置文件管理外部凭据；生产密钥由 KMS 提供** |

**不可拿来二次开发**：GraphDB Free、Stardog Free、AnzoGraph Free —— 仅免费授权，不是开源。

### 5.3 Action 模型处理（采纳优化 3，修订为受控执行）

- **MVP 不再仅保留元数据**，而是落地**受控 Action 执行引擎**：
  - Action 定义含：名称、入参、输出、语义约束、目标连接（`target_connection`）、调用方式（`mcp_tool` / `webhook` / `rest`）、入参映射（`input_map`）、**幂等键（`idempotency_key`）**、**确认模式（`confirmation`）**。
  - **回写执行路径**：本体 Action 触发 → 解析为对外部 MCP Server 写工具 / webhook 的调用 → 带鉴权 → 返回执行结果回填本体实例/执行日志。
  - **安全护栏（必须做）**：① 回写默认「`human_required` 人工确认」模式，**每次执行均需人工确认（MVP 不做自动回写）**，杜绝静默写外部系统；② 幂等键防重复回写；③ 执行结果本地日志（MVP 无完整审计，但至少留执行记录）；④ 失败指数退避重试 + 熔断；⑤ 外部系统通常无法回滚，优先幂等创建/更新。
- **示例 Action 定义（回写 CRM）**：

```json
{
  "action_id": "sync_customer_to_crm",
  "name": "同步客户到 CRM",
  "target_connection": "crm-sf-mcp",
  "invoke": { "kind": "mcp_tool", "tool": "upsert_contact" },
  "input_map": { "name": "$.Customer.name", "email": "$.Customer.email" },
  "idempotency_key": "customer::{Customer.id}",
  "confirmation": "human_required",
  "dry_run_supported": true
}
```

- **二期**再放开无条件自动回写、复杂编排、统一身份联邦。

> 对齐调研：Action 属于新一代业务本体平台的自研扩展，开源栈（Protégé/Jena）无此概念。MVP 只做「受控单动作回写」，不投入复杂工作流编排，控制单人开发成本。

## 6. 开发工程策略（采纳优化 7，不变）

1. **架构模块化拆分**：本体解析推理服务、存储适配层、MCP 服务（Server+Client）、外部数据源接入、Action 执行引擎、前端 UI、归化流水线；模块间通过 API 交互。
2. **核心模块复用开源 API**：OWL/SHACL 推理复用 Jena；MCP 传输/协议复用官方 SDK；少手写协议与语义逻辑。
3. **建立本体单元测试集 + 集成测试**：除推理/一致性回归外，**新增外部 MCP 接入 mock 测试、Action 回写 dry-run 测试**，防止 AI 迭代引入逻辑错误。

## 7. 版本规划（优化后，修订）

### 7.1 MVP 版本：本地单人模式（修订）

**目标用户**：内部建模人员、ITBP 单人试用 ｜ **核心目标**：验证本体约束降低 Agent 幻觉，并打通「读外部真实数据 → 本体约束 → Action 受控回写」业务闭环。

1. 建模能力：手工/逆向/Schema 约束/混合建模；上层业务友好 UI，底层映射 W3C OWL2-RL + SHACL。
2. 推理能力：概念约束、业务关系推导、推理链路可追溯可视化；本体版本快照；SHACL 一致性校验。
3. 实例归化：文档/数据表/**外部 MCP 读取**生成候选实例，必须人工审核后入库；支持自定义 LLM endpoint。
4. 可视化：本体视图、知识图谱视图（区分外部来源溯源）、推理链路视图。
5. 模板：预置模板，支持加载预览外部网络模板。
6. MCP **双向**：① Server 端 UI 一键发布，输出本体查询、推理溯源工具；② **Client 端 UI 配置接入外部含鉴权数据平台 MCP Server**，读取数据。
7. **Action 受控执行**：本体 Action 可对外部平台数据回写（人工确认 + 幂等 + 执行日志）。
8. 存储：混合存储（Jena 推理服务 + Neo4j 实例存储 + pgvector 向量）；**凭据加密存储**。
9. **不包含**：多租户、部门隔离、审批流、细粒度血缘、完整审计、RBAC、无条件自动回写、复杂 Action 编排、流式 CDC。

### 7.2 V2.0 服务端版本（多部门协同，企业级落地，修订）

1. 部署迁移 K8s 云原生，支持多租户，部门、工作组共享 / 数据隔离。
2. 补齐全套企业治理：版本审批流、血缘映射、完整审计日志、细粒度权限。
3. Action 执行引擎增强：复杂编排、无条件自动回写、统一身份联邦。
4. 扩展消费接口：SPARQL、REST、GraphQL。
5. 对接数据治理模块基础能力。

### 7.3 V3.0 远期（不变）

1. BI 可视化消费能力。2. 本体资产市场、模板库共享。3. 更多数据接入适配器。

## 8. 关键风险清单与缓解（优化后，修订）

| 风险 | 影响 | 缓解手段 |
|---|---|---|
| ITBP 使用门槛高，建模产出差，业务见效慢 | 项目业务价值无法落地 | 上层封装业务建模层；提供模板；小范围试点收集反馈；强制实例人工审核 |
| 单人 + AI 编码，代码质量差，维护困难 | 后期 bug 多，推理逻辑错误 | 模块化架构；核心语义/MCP 复用开源组件，少手写；建立本体 + 外部 MCP mock + Action dry-run 测试集 |
| 源系统数据质量差，自动归化产生脏实例 | 本体错误，加剧 Agent 幻觉 | 归化流水线强制人工审核卡点；SHACL 校验；外部 MCP 接入首次/变更须人工确认 |
| Java/Python 混合栈集成复杂度高 | 稳定性、部署复杂度上升 | Jena 独立 HTTP 服务，Python 只调用 API |
| 过早引入全套企业级治理，MVP 膨胀 | 周期拉长，看不到业务效果 | 治理能力分层，MVP 只保留快照/一致性校验，审批多租户后置 V2 |
| **【新增】外部凭据管理（Demo 轻量化）** | 本地明文存外部 API Key 存在泄露隐患 | Demo 以本地 env/配置文件管理外部凭据（`chmod 600`、不入库不打印）；加密落盘与 KMS 作为生产必做项后置；本体平台自身不实现登录鉴权，由外部平台负责 |
| **【新增】Action 误回写 / 重复回写外部系统** | 污染外部业务系统、不可逆损失 | **默认人工确认模式；幂等键防重；dry-run 优先；失败熔断；外部系统优先幂等更新** |
| **【新增】外部 MCP 平台不稳定 / schema 漂移** | 读取失败或脏数据入库 | 健康检查 + 超时 + 重试退避；schema 漂移即停自动入库转人工；401/403 阻断并告警，不静默降级 |
